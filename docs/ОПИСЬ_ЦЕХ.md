# ЦЕХ — функциональная опись системы (Google Apps Script)

Источник: `/home/user/Brave-haccp/gas` (≈140 файлов .gs, 29,5 тыс. строк; `Index.html` — 5415 строк), `STAGE*.md`.
Метод: `CONFIG.ACTION_MODULE` вычислен программно (node + vm из `Config.gs`); набор действий `ACTION_HANDLERS`
(API.gs и дописки `ACTION_HANDLERS.X =`) сопоставлен со строковыми литералами действий в `Index.html`.
Если действие вызывается из интерфейса, оно считается «с экраном». Действия без `_` (LOGIN, LOGOUT) и действия
с динамически собранным именем могли не попасть в подсчёт. Поэтому доли «UI x/y» приблизительные, но порядок величин верный.

## 1. Склад и приход (накладные, OCR)
**Модули:** warehouse_receive (25 действий, в UI 17), warehouse_view (17, в UI 10). **Файлы:** Warehouse.gs, InvoiceRecognitionCore.gs, InvoiceOcr.gs, EnterpriseIntake.gs, OperationalClosureStage11/12/13.gs, OcrYandex.gs (этикетки), FiscalQrCore.gs, ReceiptCorrectionCore.gs, MercuryCore.gs (см. п. 1a), Compliance.gs (проверка при приёмке).
- **Назначение.** Склад ведётся как журнал движения: остаток не вводится руками, а равен сумме непотраченных остатков партий (BATCHES). Приход оформляется вручную или по фото/PDF накладной.
- **Действия.** RECEIVE_GOODS(_BATCH), TRANSFER_STOCK, SCAN_INVOICE_PREVIEW → UPDATE_INVOICE_DRAFT / SCAN_INVOICE_LINE_LABEL → CONFIRM_INVOICE_RECEIPT; ATTACH_FISCAL_QR; CREATE_RECEIPT_CORRECTION (утверждает DECIDE_RECEIPT_CORRECTION в audit_admin); RUN_PRODUCT_LABEL_OCR / MATCH_PRODUCT_FROM_LABEL / CREATE_PRODUCT_FROM_OCR; CHECK_RECEIPT_COMPLIANCE; GET_WAREHOUSE, FIND_PRODUCT_BY_BARCODE, GET_INVOICE_DRAFTS, GET_RECEIPT_BATCHES, GET_RECEIPT_CORRECTIONS.
- **Таблицы.** WAREHOUSE_OPS, BATCHES, PRICE_HISTORY, INVOICE_INTAKE_DRAFTS, INVOICE_DOCUMENTS, OCR_ALIASES, OCR_RESULTS, FISCAL_QR_EVIDENCE, RECEIPT_CORRECTIONS.
- **Механика.**
  - Распознавание: Yandex Vision (модель page, при рукописном или слабом тексте второй проход handwritten; многостраничный PDF обрабатывается асинхронно) → таблица по координатам слов с поправкой на наклон → YandexGPT извлекает реквизиты и строки → детерминированная проверка «кол-во × цена = сумма», при сомнениях второй проход модели → сопоставление строки: штрихкод → артикул → подтверждённый алиас поставщика → точное название → нечёткий поиск (Левенштейн).
  - Черновик проверяется на целостность документа (отпечатки документа и строк ловят повтор накладной) и проходит ХАССП-решение по каждой строке (`runHaccpDecisionEngine_`). Перед проводкой выполняется строгий preflight (Stage 12).
  - QR кассового чека сверяется по сумме, дате и ФН/ФД. Тот же чек в другой приёмке блокирует черновик; чек «возврат прихода» даёт предупреждение.
  - Проводка (`receiveGoods_`): проверка комплаенса (в режиме BLOCKING приход запрещается) → партия → автоматическая маркировка партии (createBatchMarking_) → средневзвешенная цена → PRICE_HISTORY → каскад Food Cost → аудит → автоматическая генерация задач разбора по утверждённой карте разбора (BreakdownCore).
  - Списание идёт по FIFO/FEFO. Просроченные, ожидающие ВСД и заблокированные партии в «годный» остаток не входят (`getUsableStockLevel_`).
  - Корректировка проведённой накладной идёт по принципу «предложение → утверждение другим человеком». Количество можно уменьшить только на неизрасходованную часть; при изменении цены пересчитываются средневзвешенная цена и себестоимость блюд.
- **Экран.** «Склад»: ДИР, ШЕФ (только просмотр), КЛАД, ТЕХ (просмотр). Блоки приёма видны только с warehouse_receive.
- **Зрелость: работает полностью**, это ядро системы. Без UI остались recall-кейсы, CONFIRM_BATCH_SHELF_LIFE, APPEND_INVOICE_INTAKE_PAGE, RESOLVE_INVOICE_INTAKE_LINE, дашборд целостности, паспорт и QR партии, рекурсивная себестоимость партии.

### 1a. ФГИС «Меркурий» (ВСД)
- **Действия.** FETCH_VSD, LINK_VSD_TO_DRAFT_LINE, LINK_VSD_TO_BATCHES, REJECT_VSD, MAP_MERCURY_SUPPLIER, GET_VSD_LIST, CHECK_VSD, SYNC_VSD, CANCEL_VSD (числится в модуле ppk), SAVE_MERCURY_CONFIG / TEST_MERCURY_CONNECTION (configuration_admin). **Таблицы.** VET_DOCUMENTS, MERCURY_EXCHANGE_LOG, MERCURY_SUPPLIER_MAP.

Входящие ВСД отбираются по номеру накладной и поставщику и сопоставляются со строкой черновика. Ветеринарно подконтрольная партия без погашенного ВСД получает статус ОЖИДАЕТ_ВСД и не участвует в остатке и производстве. Погашение (processIncomingConsignment) переводит партию в статус «активна». Повторного гашения нет. Без настроенной интеграции гашение не имитируется. Каждый час работает триггер `mercurySyncPendingTrigger_`.
- **Экран.** Блок «ВСД («Меркурий»)» на складе. **Зрелость: реализовано полностью, работоспособность зависит от реальных учётных данных ВетИС.** Настройка подключения в UI отсутствует.

## 5. Рецепты и фудкост
**Файлы.** Recipes.gs, FoodCost.gs, PriceCascade.gs, Products.gs (UPDATE_PRODUCT_PRICE).
- **Механика.** Каскадный пересчёт себестоимости, food cost и маржи по DISHES — единственное место, где эти поля пишутся. Пересчёт запускается сменой цены продукта и приходом (средневзвешенная цена). **Модули:** auth, users (11 действий, в UI 5), locations, organizations (только ADMIN, без UI). **Файлы.** Auth.gs, Users.gs, Organizations.gs, EmployeeSafetyIntegration.gs (должности, перевод), PeriodLockStage34.gs, Idempotency.gs, Setup.gs, Deploy.gs.
- **Механика.** PIN уникален в пределах организации, хранится как хэш SHA-256. Блокировка лестницей. Отключённый пользователь теряет доступ со следующего запроса. Location-scope проверяется на сервере. Защищённые поля вырезаются из patch (`_stripProtectedFields_`). Проверяется, что точки сотрудника принадлежат его организации. Есть блокировка закрытого периода.
- **Экран** «Сотрудники» (создать, сбросить PIN, (де)активировать): ДИР. Должности, профиль, перевод и смена PIN доступны **только через API**. **Зрелость: работает**, кадровая часть частично.
- **Найденный дефект конфигурации.** В `Config.gs` (строки 1219–1227) **67 действий модуля `enterprise_control`** (Stage 42–90) записаны **после закрывающей `}` объекта ACTION_MODULE**, то есть как свойства самого `CONFIG`. Поэтому `CONFIG.ACTION_MODULE[action]` для них не определён, и processOperation отклоняет их всем, включая ADMIN. Так же не зарегистрированы GET_CORE100_HARDENING_STATUS, CREATE_GLOBAL_PRODUCT_FROM_OCR и 5 действий Demand Planning. При этом в ROLE_MODULES модуль `enterprise_control` выдан ДИРЕКТОРУ, БУХГАЛТЕРУ и МЕНЕДЖЕРУ.

## 24. Мастер ППК (PpkWizardCore.gs, Stage 115)
- **Назначение.** Пошаговая сборка «цифрового предприятия», из которой строятся модель ППК, журналы и документ.
- **Шаги.** 1 Предприятие (тип: ресторан, кафе, столовая, фабрика-кухня, кейтеринг, доготовочное; мощность; режим) → 2 Помещения и зоны с площадью → 3 Оборудование по категориям с привязкой к помещению → 4 Инвентарь и маркировка → 5 Дезинфекция (расчёт количества средства по площади, режимы со статусом «сверить по инструкции») → 6 Номенклатура и ТТК → 7 Процессы и потоки → 8 Анализ опасностей → 9 Контроль и пределы → 10 Журналы (включая журналы оборудования) → 11 Документ ППК (просмотр, печать, PDF, утверждение).
- **Механика.** У каждого шага статус-светофор и список недостающего. Принцип «система предлагает типовой состав, человек отмечает реальное»: предложение ничего не создаёт само, ни одна позиция не отмечена заранее. Таблицы: PPK_ENTERPRISE, PREMISES, INVENTORY_ITEMS, DISINFECTANTS, DISINFECTION_PLANS (+ EQUIPMENT).
- **Действия.** GET_PPK_WIZARD, SAVE_PPK_ENTERPRISE, PROPOSE/SAVE/UPDATE/ARCHIVE_PPK_PREMISE(S), PROPOSE/ADD/BIND/UPDATE/ARCHIVE_PPK_EQUIPMENT, PROPOSE/ADD/UPDATE/REMOVE_PPK_INVENTORY, SAVE/ARCHIVE_PPK_DISINFECTANT, SAVE/REMOVE_PPK_DISINFECTION_PLAN, CREATE_PPK_EQUIPMENT_JOURNALS, GET_PPK_DOCUMENT_VIEW, PRINT_PPK_DOCUMENT. **Все есть в UI.**
- **Экран.** «ППК» → «Мастер ППК — цифровое предприятие»: ДИР, ТЕХ. **Зрелость: работает полностью** (новейший модуль).

## 25. Критические инциденты / карантин

## 26. AI

## 27. Интеграции

## 28. Offline-очередь
**Модуль:** offline (2 действия). Сервер принимает ENQUEUE и SYNC (allowlist действий, защита от рекурсии). В UI `queueOfflineUI` определена, но **нигде не вызывается**. `syncOfflineUI` отправляет пустой список и затем стирает локальную очередь. **Фактически заглушка на стороне клиента.**

## 31. Функции ЦЕХ, нехарактерные для типичной кухонной системы
1. **Мастер ППК «цифровое предприятие»**: 11 шагов от помещений и площадей до документа ППК, расчёт дезсредства по площади, журналы оборудования.
2. **Генератор ППК / HACCP**: процессы → потоки → анализ опасностей → OPRP/КТ/ККТ → пределы с утверждением человеком → журналы и лабораторная программа, версионирование и шлюз готовности.
3. **ККТ из ТТК в ППК и журналы «по партии»**: предложение ККТ из технологии блюда или ПФ, решение технолога, перенос в черновик ППК, журнал, запись при выпуске каждой партии.
4. **ТУ по ГОСТ Р 51740-2016 прямо из ТТК**: КБЖУ по ТР ТС 022/2011 с потерями при тепловой обработке, рецептура на 100 кг, физико-химические показатели с допуском, статус «ПРОЕКТ» до протокола лаборатории.
5. **Нормативный срок годности**: срок блюда как самый строгий из норм групп продукции и ПФ, протокол по МУК 4.2.1847-04 при превышении, справочник норм со статусом «не проверено».
6. **ФГИС «Меркурий» в приёмке**: ВСД сопоставляется со строкой накладной, партия ОЖИДАЕТ_ВСД до гашения и исключена из остатка и производства.
7. **QR фискального чека как доказательство**: сверка ФН/ФД/ФП, суммы и даты, блокировка повторно проведённого чека, распознавание «возврата прихода».
8. **Импорт архива ТТК и синхронизация с Google Диском**: 560 карт FastReport XML, Excel, Word, PDF; diff «было → стало»; защита от «опустевшей папки»; проверка технологом.
9. **OCR банкетного бланка**: выпрямление снимка, арифметический контроль, сопоставление с ТТК, автоматический расчёт сырья мероприятия.
10. **Охрана труда, связанная с допуском к оборудованию**: матрица требований по должности, цеху и оборудованию → автоназначение инструктажей → тест → допуск, проверка допуска перед операцией, аварийные инструкции по QR.
11. Дополнительно: акты разбора сырья с автоматическими задачами от прихода; hash-chain аудита (append-only хранилище); корректировки приёмки с принципом «двух ключей»; маркировка «вскрытой тары» с новым сроком; декларации соответствия с режимом BLOCKING при приёмке; журналы, которые система не заполняет сама («не фальсифицировать»).
