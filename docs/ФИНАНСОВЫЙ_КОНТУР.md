# Финансовый контур ЦЕХ: логика, формулы, отчёты

Документ описывает, как в ЦЕХ движутся товар и деньги — от накладной поставщика до прибыли и бюджета. Статусы такие:
**есть** — работает в коде (указан модуль), **пробел** — не сделано, план внизу (раздел 13).

Контур **управленческий**. Бухгалтерскую и налоговую отчётность ведёт 1С или бухгалтер. На каждом отчёте ЦЕХ стоит пометка
«Отчёт управленческий. Не является бухгалтерской или налоговой отчётностью» (`MGMT_NOTE`, `ops/finance.ts`).

---

## 0. Правила контура

1. **Неизвестное — не ноль.** Если у партии нет цены, у продажи нет списания или нет ФОТ, итог помечается как неполный
   с перечнем причин. Пустое значение никогда не подставляется нулём.
2. **Один источник правды для каждой цифры.** Цена товара берётся только из строки приёмки. Выручка — только из таблицы
   продаж `sales`, деньги — из оплат `pos_payments`. Себестоимость продажи — только по фактически списанным партиям.
3. **Проведённое не меняется.** Оплаты, движения склада, утверждённые калькуляции и аудит нельзя изменить даже напрямую
   в базе. Ошибка исправляется новой записью с причиной: возвратом, аннулированием или новой калькуляцией.
4. **Расчёт не записывается как факт.** Норма по ТТК — это план. Факт — это списанные партии.
5. **«Сегодня» и границы периода — в часовом поясе организации.** Период считается от 00:00 первого дня до 24:00
   последнего дня по местному времени.
6. **Цены видит только тот, кому положено.** Цены закупки и себестоимость — право `cost.read`. Выручка и отчёты —
   `econ.read`, ввод расходов и бюджета — `expense.manage`. Повар, кассир и кладовщик цен закупки не видят.
7. **Защита от повтора.** Повтор оплаты, расхода или приёмки с тем же `operationId` возвращает первый результат
   и не проводит операцию второй раз.

## 1. Общая схема

```
 Заказ поставщику ──► Приёмка (накладная) ──► Партия с ценой ──┬─► Производство п/ф ─► Партия п/ф (цена = снимок расчёта)
 (ops/purchasing)     (ops/receipts)          (lots.unit_price) │
                                                                ├─► Продажа блюда ─► списание по ТТК (FEFO) ─► себестоимость продажи
 Фото / QR чека ──► распознавание ──► строки накладной          ├─► Мероприятие (банкет) ─► расход по меню
 (ops/recognition)                                              ├─► Списание (потери по классам)
                                                                ├─► Перемещение / вскрытие тары (цена наследуется)
                                                                └─► Инвентаризация (недостача / излишек)

 Касса ЦЕХ (заказ → оплата → возврат) ──► sales + pos_payments ─┐
 Импорт продаж iiko / r_keeper (CSV)  ──► sales ────────────────┤
 Расходы (ФОТ, аренда, …)            ──► expenses ─────────────┼─► P&L ─► отчёты ─► план-факт с бюджетом
 Бюджет по месяцам                    ──► budgets ──────────────┘          └─► ДДС (движение денег)
```

## 3. Накладная (приёмка)

**Есть** (`ops/receipts.ts`, `ops/recognition.ts`, `recognition/*`):

- **Шапка накладной:** поставщик, номер и дата документа, площадка. Приёмку можно начать из заказа поставщику,
  тогда заказ отмечается полученным.
- **Строка накладной:** товар, количество, единица, **цена за единицу**, партия изготовителя, даты изготовления
  и годности (с основанием), температура, проверки (упаковка, маркировка, документы, качество), решение
  (принято / карантин / отказ с причиной), изготовитель, номер ВСД.
- **Ввод с фото.** ТОРГ-12, УПД и фото накладной распознаются через Yandex Vision и YandexGPT в черновик строк.
  Человек проверяет черновик и принимает накладную целиком одним действием. Это платная функция, её включает владелец.
  QR-код кассового чека даёт ФН, ФД, ФП и сумму.
- **Завершение приёмки:**
  1. на каждую принятую строку создаётся партия с ценой: `lots.unit_price` = цена строки;
  2. отклонённые строки на склад не попадают;
  3. включается каскад цен: какие товары подорожали или подешевели и какие блюда это затронуло
     (`ops/priceImpact.ts`), уведомление шефу и бухгалтеру.
- **Сумма накладной** = Σ (количество × цена) по принятым строкам. Строка без цены даёт неполную сумму
  и попадает в «Полноту данных».

**Сделано (Ф-2): деньги накладной** (`ops/receipts.ts`, миграция 066).

Решение владельца: режим налогообложения — **АУСН или патент** (выбирается в настройках предприятия). Оба — без НДС к вычету,
поэтому **себестоимость товара — полная цена с НДС поставщика**. Ставки НДС в коде не задаются: берутся из документа.

| Поле | Где | Смысл |
|---|---|---|
| Цены в документе с НДС / без НДС | накладная (по умолчанию — настройка предприятия) | как поставщик указал цены |
| Цена в документе | строка (`doc_price`) | как напечатано |
| Ставка НДС, % | строка (`vat_rate`); пусто — «без НДС» | из документа; при распознавании берётся, только если значение похоже на ставку |
| Цена для себестоимости | строка (`unit_price`) | с НДС: если цены «без НДС», `цена × (1 + ставка / 100)` |
| Итог документа «Всего к оплате» | накладная (`doc_total`) | из документа или распознавания |
| Доставка, тара | накладная (`extra_costs` + что это) | распределяются на принятые строки пропорционально сумме, входят в цену партии |

```
сумма строки (с НДС)     = количество × цена для себестоимости
НДС в т. ч.              = сумма строки × ставка / (100 + ставка)
по документу             = Σ сумм ВСЕХ строк (как в документе, включая отказанные)
к оплате поставщику      = Σ сумм принятых и карантинных строк + доставка и тара
срок оплаты              = дата документа (или приёмки) + отсрочка поставщика (дней, из договора поставки)
цена партии              = цена для себестоимости + доля доставки на единицу
```

- **Сверка с итогом.** При завершении сумма по документу сравнивается с итогом. Допуск — копейка на строку.
  Не сходится — завершить можно только с причиной (недовоз, пересорт, акт). Бухгалтер получает уведомление.
  Накладная без итога документа попадает в «Полноту данных».
- **Неизвестное — не ноль.** Если у принятой строки нет цены, сумма к оплате «не определена».
- Суммы фиксируются **снимком** при завершении (`lines_total`, `vat_total`, `payable`, `due_date`) и дальше не меняются.
- Отчёт «Закупки по поставщикам» показывает: по документам, НДС в т. ч., доп. расходы, к оплате, накладные без цены,
  без номера, без итога.

**Осталось:** корректировка (УКД) и возврат поставщику в деньгах — этап Ф-3 вместе с оплатами и долгами.

## 4. Оценка запаса: у каждой партии своя цена

**Есть.** Учёт ведётся по партиям: каждая партия хранит свою цену, усреднения на складе нет.

| Как появилась партия | Цена партии | Где |
|---|---|---|
| Приёмка | цена строки накладной | `receipts.ts` |
| Производство п/ф | **снимок расчёта** `lots.cost_basis`: Σ (списанное количество × цена входной партии) ÷ выход; входные партии, формула и метод сохраняются | `production.ts` |
| Вскрытие тары, перемещение | цена исходной партии | `stock.ts` |
| Хоть у одной входной партии нет цены | `null` — «неполная», не 0 | — |

- **Расход** идёт только по FEFO: сначала партии с ближайшим сроком, готовые п/ф раньше сырья. Себестоимость расхода
  = Σ (списанное количество × цена этой партии). Получается оценка «по себестоимости каждой партии».
- **Баланс партии** (`ops/lotEconomics.ts`):
  `приход + выпуск + получено − расход − передано − списано ± инвентаризация = расчётный остаток`.
  Расчётный остаток сверяется с фактическим. Расхождение показывается, а не подгоняется.
- **Классы потерь** считает функция `loss_class` в базе:

  | Класс | Причины |
  |---|---|
  | технологические | потери при обработке |
  | санитарные | порча, брак, карантин, отзыв |
  | аварийные | повреждение |
  | коммерческие | истёк срок |
  | необъяснённые | «другое», недостача по инвентаризации |

**Исправлено (Ф-1):** плановая цена товара (`productPrice`, `ops/recipes.ts`) усредняется только по партиям в единице товара.
Партии в другой единице (если единицу товара поменяли) в среднюю не входят. Средняя считается по всем площадкам
предприятия: это цена для меню, а себестоимость продажи берёт партии своей площадки.

## 5. Калькуляция: план, снимок, факт

Себестоимость блюда в ЦЕХ существует в трёх видах. Смешивать их нельзя.

### 5.1. Плановая (живая) себестоимость — **есть** (`recipes.ts → calcVersion`, `priceImpact.ts → dishCosts`)

```
цена товара     = средневзвешенная по остатку годных партий  Σ(остаток × цена) / Σ остаток
                  иначе — цена последней закупки; иначе — нет цены (себестоимость неполная)
строка ТТК      = брутто, переведённое в единицу цены (только по подтверждённому коэффициенту) × цена
полуфабрикат    = себестоимость его утверждённой ТТК на 1 кг выхода × масса в блюде (вложенность до 5 уровней)
себестоимость   = Σ строк                        — на выход ТТК
на порцию       = себестоимость × выход порции / выход ТТК
п/ф на 1 кг     = себестоимость × 1000 / выход ТТК
фудкост, %      = себестоимость порции / цена продажи × 100
наценка, %      = (цена продажи − себестоимость) / себестоимость × 100
маржа, ₽        = цена продажи − себестоимость порции
```

Плановая себестоимость считается при каждом показе. После каждой приёмки каскад цен показывает «было → стало»
по товарам и блюдам. Изменения меньше 0,5 % каскад не показывает.

### 5.2. Калькуляционная карточка ОП-1 — **есть** (`ops/costing.ts`)

- Составляется только по **утверждённой** ТТК. Норма — брутто на 1 блюдо (п/ф — на 1 кг) в единице цены.
- Расчёт: сумма строки = норма × цена; себестоимость блюда = Σ сумм; сырьевой набор на 100 блюд = × 100;
  наценка — как в 5.1.
- Если цены нет, её вводит человек **с основанием**. В карточке видно, откуда каждая цена: средняя по остатку,
  последняя закупка или «вручную: основание».
- Утверждённая карточка — **снимок** и не меняется. Новые цены — новая карточка.

### 5.3. Себестоимость продажи — **есть** (`pos.ts → fulfilSale`, `bom.ts`)

Как продажа влияет на склад, выбирает предприятие (настройка организации `sales_consumption`):

| Режим | Что делает продажа | Себестоимость продажи |
|---|---|---|
| **Расчётное потребление** (по умолчанию) | склад **не меняет**, пишет расчёт по ТТК (`consumption_estimates`); сырьё уходит со склада через расход, списание и инвентаризацию | по ТТК × цены партий в очереди FEFO |
| **Списание по ТТК** | списывает сырьё по ТТК через FEFO (движения помечены «расчётное списание») | Σ цен фактически списанных партий |

- В обоих режимах себестоимость продажи — это **расчёт по ТТК**. Фактический расход сырья виден только по складу:
  потери, недостачи, прочий расход (раздел 8 и отчёт «Сверка склада»).
- Если списать нельзя (нет ТТК, не хватает годного остатка, название не сопоставлено), оплата проходит,
  а продажа попадает в очередь с причиной. Шеф получает задачу. «Повторить списание» проводит её позже.

**К-1 — сделано (Ф-1):** «по ТТК против факта» считается по всему складу в отчёте «Сверка склада и фактический фудкост»
(раздел 9). По отдельному блюду факт не определить: и при продаже, и при списании по ТТК расход — это расчёт, а не взвешивание.

## 6. Продажи, касса, выручка

**Есть** (`ops/pos.ts`):

- **Смена.** Открывается с наличными на начало; на площадке одна открытая смена. X-отчёт: оплаты по способам,
  возвраты, средний чек, ожидаемые наличные. При закрытии вводится факт наличных, расхождение сохраняется как есть.
  Закрыть смену с неоплаченными заказами нельзя.
- **Заказ.** Цена берётся на сервере из карточки блюда и сохраняется снимком в позиции. Стоп-лист проверяется.
- **Оплата:** наличные, карта, прочее или смешанная. Безнал — не больше суммы заказа, сдача — только с наличных.
- **Возврат** делает руководитель: в открытой смене, отрицательной оплатой и отрицательной продажей.
  Безналом можно вернуть не больше, чем им оплачено. Сырьё на склад не возвращается.
- **Импорт внешней кассы** (iiko, r_keeper, другая) — CSV. ID строки уникален, поэтому повтор не дублирует продажи.
  Неизвестное название уходит в очередь сопоставления; сопоставленное один раз списывается сразу.
- **Фискализация** — на ККТ предприятия. ЦЕХ её не заменяет.

```
валовая выручка   = Σ amount продаж с qty > 0
возвраты          = −Σ amount продаж с qty < 0
чистая выручка    = валовая − возвраты
заказов           = число различных заказов (касса ЦЕХ) или чеков (импорт)
средний чек       = чистая выручка / заказов
ожидаемые наличные смены = наличные на начало + оплаты наличными − возвраты наличными
расхождение смены = факт наличных − ожидаемые
```

**Пробелы:**

| № | Чего нет |
|---|---|
| К-2 | **Выемка, внесение и инкассация наличных, расходы из кассы.** Сейчас ожидаемые наличные не учитывают выдачу денег из кассы, и такая выдача видна как расхождение |
| К-3 | **Мероприятия в P&L — сделано (Ф-1):** «Проведено» создаёт продажи с источником «мероприятие» (выручка по меню, себестоимость — списанные партии); проведённые раньше восстановлены миграцией 065. Предоплаты (авансы) — этап Ф-3 |
| К-4 | **Скидки и обслуживание** отдельной строкой не ведутся: скидка видна только как меньшая цена |

## 7. Расходы предприятия

**Есть** (`ops/finance.ts`):

- **Статьи:** ФОТ, аренда, коммунальные, маркетинг, услуги, оборудование и ремонт, налоги и сборы, эквайринг,
  доставка, прочее.
- **Вид расхода:** разовый — на дату; ежемесячный — на месяц, в период попадает доля дней:
  `в периоде = сумма × (дней месяца внутри периода / дней в месяце)`.
- Расход привязан к площадке или ко всему предприятию. Его можно аннулировать с причиной, удалить нельзя.

**Пробел Р-1:** ФОТ вводится вручную. Из табеля и ставок он не считается: учёта рабочего времени в системе нет.

## 8. P&L — отчёт руководителя

**Есть** (`ops/finance.ts → pnl`). Формулы:

```
чистая выручка          = валовая − возвраты
себестоимость продаж    = Σ cost продаж, по которым прошло списание и известна цена всех партий
валовая прибыль         = чистая выручка − себестоимость продаж
потери                  = Σ (−количество × цена партии) по движениям «списание»
ФОТ                     = расходы статьи «ФОТ» в периоде
прочие расходы          = остальные статьи в периоде
управленческая прибыль  = валовая прибыль − потери − ФОТ − прочие расходы
Prime Cost              = себестоимость продаж + ФОТ
фудкост, %              = себестоимость / выручка ПО ПРОДАЖАМ С ИЗВЕСТНОЙ СЕБЕСТОИМОСТЬЮ × 100
наценка, %              = (выручка_с_себест − себестоимость) / себестоимость × 100
маржинальность, %       = (выручка_с_себест − себестоимость) / выручка_с_себест × 100
доли статей, %          = статья / чистая выручка × 100
```

**Статус полноты цифр** проставляется автоматически с причинами:

| Статус | Когда |
|---|---|
| **неполный** | есть продажи без ТТК, без списания или без цены; партии или списания без цены |
| **ориентировочный** | себестоимость полная, но нет ФОТ, аренды или коммунальных; есть оплаты картой без расхода на эквайринг |
| **есть неподтверждённые данные** | приёмки без номера документа; продажи из импорта, которые сверяются с ККТ вне системы |
| **полный** | причин нет |

**Сделано (Ф-1): всё, что ушло со склада, попадает ровно в одну строку P&L.**

| Строка P&L | Откуда |
|---|---|
| Себестоимость продаж | продажи кассы и импорта + **мероприятия** |
| Списания (потери) | списания по причинам |
| Инвентаризационные разницы | недостачи − излишки. **Только в режиме «списание по ТТК».** В режиме «расчётное потребление» недостача включает проданное (оно уже в себестоимости), поэтому в прибыль не вычитается: статус «ориентировочный» с причиной и ссылкой на «Сверку склада» |
| Питание персонала и проработки | ручной расход с назначением «питание персонала» или «проработка, дегустация» — отдельная статья по решению владельца |
| Прочий расход сырья | ручной расход с назначением «прочий» |

Ручной расход со склада теперь требует назначения. Провести вручную «продажу», «мероприятие» или «производство» нельзя:
их списывают свои модули.

Сверка склада за период (отчёт «Сверка склада и фактический фудкост»):

```
запас на начало + закупки − возвраты ± производство, тара, перемещения
   − расход по продажам (только при списании по ТТК) − мероприятия − питание персонала − прочий расход
   − списания − недостачи + излишки = запас на конец            (проверка: расхождение 0,00)

фудкост по ТТК       = (себестоимость продаж + мероприятий) / чистая выручка
фактический фудкост  = (всё, что ушло со склада, кроме питания персонала, производства, перемещений и возвратов) / чистая выручка
разница факт − ТТК   = потери + прочий расход + инвентаризационные разницы сверх ТТК
```

Запас на любую прошлую дату восстанавливается по журналу движений (он неизменяем) и цене партии, снимки не нужны.
Фактический фудкост точен, когда на конец периода проведена инвентаризация; дата последней показывается в отчёте.

## 10. Движение денежных средств (ДДС)

**Есть:** поступления кассы ЦЕХ по способам оплаты, возвраты покупателям, расходы по датам внесения.

**Не хватает до полного ДДС:**

1. оплат поставщикам (Н-4);
2. выписки банка — импорт в формате обмена 1С «Клиент-Банк» (`1CClientBankExchange`) с разнесением по статьям;
3. денег из внешних касс: сейчас продажи iiko и r_keeper есть в выручке, но не в деньгах;
4. эквайринга как удержания банка, а не только как расхода;
5. инкассации и выемки (К-2);
6. авансов за мероприятия (К-3).

Правило: ДДС считается **по дате движения денег**, P&L — **по дате продажи или расхода**. Это разные отчёты, и их
итоги не обязаны совпадать.

## 11. Бюджет

**Есть.** Бюджет вводится по месяцам и статьям (чистая выручка и статьи расходов), по площадке или по предприятию.

## 13. Чего не хватает до полного контура — план работ

Порядок выбран так, чтобы сначала прибыль перестала быть завышенной, потом появились долги и деньги, потом —
связь с бухгалтерией.

**Этап Ф-1. Честный P&L (без решений владельца, кроме вопроса 4).**

1. **П-1, П-4:** недостачи и излишки инвентаризации — в P&L строкой «Инвентаризационные разницы».
2. **П-2:** прочий расход со склада — строкой «Прочий расход сырья» с разбивкой по основаниям. Для питания
   персонала добавить отдельное основание.
3. **К-3, П-3:** мероприятие при проведении создаёт продажи с источником «мероприятие» и выручкой по меню.
   Себестоимость = списанные партии. После этого банкеты видны в P&L, ABC и по каналам.
4. **Сверка склада за период** — формула из раздела 8. Нужен З-1: ежедневный снимок стоимости запаса по площадкам.
5. **К-1:** отчёт «План-факт себестоимости блюда» — норма ТТК по ценам списанных партий против фактически списанного.
6. Исправить риск усреднения цены по разным единицам (раздел 4).

**Этап Ф-2. Накладная полностью (нужны ответы владельца на вопросы 1–2).**

1. **Н-1:** в строке — ставка НДС, сумма НДС, цена без НДС и с НДС. В организации — признак «плательщик НДС».
   Себестоимость берёт цену без НДС у плательщика и с НДС у неплательщика. Ставки не зашиваются в код, а берутся
   из документа поставщика.
2. **Н-2:** итог документа, сверка с суммой строк, допуск на округление — копейки по числу строк.
3. **Н-5:** доп. расходы поставки, распределённые на строки пропорционально сумме.
4. **Н-3:** корректировка (УКД) и возврат поставщику с суммой.

**Этап Ф-3. Долги и деньги (нужен ответ на вопрос 3).**

1. **Н-4:** оплаты поставщикам (дата, сумма, способ, какие накладные гасит), кредиторка по поставщикам
   и срокам из договора (`contracts`), календарь платежей.
2. **К-2:** внесение, выемка, инкассация, расход из кассы — в X-отчёте и в ожидаемых наличных.
3. Авансы за мероприятия, остаток к оплате, дебиторка.
4. Импорт банковской выписки 1С «Клиент-Банк» с правилами разнесения по статьям.
5. Полный ДДС, остатки денег на начало и конец (касса и счёт).

**Этап Ф-4. Закрытие и обмен.**

1. **З-2:** закрытие месяца. Проверки: нет черновиков приёмки, нет очереди списаний, инвентаризация проведена,
   ФОТ внесён. После закрытия запись задним числом запрещена, а отчёты фиксируются с хешем.
2. Выгрузка в 1С: закупки, реализация, списания за период. Формат согласуется с бухгалтером.
3. **З-3:** распределение общих расходов по площадкам.
4. Целевой фудкост в бюджете и сигнал о превышении.
5. Интеграции, для которых нужны доступы владельца: iiko API (вместо CSV), ЭДО (УПД без фото), ФГИС «Меркурий»
   (ВСД в приёмке).
