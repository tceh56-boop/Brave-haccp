# ЦЕХ — этап 8: пилот на одном объекте

Документ для владельца, ответственного за ХАССП и того, кто разворачивает систему. Он основан на ТЗ v2: §9, §15 (этап 8) и §16 (Definition of Done).

Состояние готовности конкретного предприятия система показывает сама: **«Управление → Готовность к пилоту»**. Там же принимается решение «Запускаем / Не запускаем». Решение сохраняется вместе со снимком всех проверок и не меняется.

## 1. Что проверяет система перед запуском

| Группа | Проверка | Блокирует запуск |
|---|---|---|
| Организация и команда | Реквизиты (форма, ИНН) | нет |
| | Есть двое, кто может работать с отклонениями и подтверждать их закрытие | **да** |

| | Нет просроченных CAPA; журналы подписываются | нет |

Подтверждения дают владелец, администратор или директор. К каждому подтверждению нужно основание: кто подтвердил и каким документом. Подтверждение можно отозвать — тогда запуск снова блокируется.

## 2. Развёртывание для пилота

Рабочий сервер — **Yandex Cloud**, данные в РФ. Пошаговая инструкция и установка одной командой — `docs/РАЗВЁРТЫВАНИЕ_YANDEX_CLOUD.md`. Ниже — что под капотом.

* **Сервер:** Node.js 22, PostgreSQL 16, HTTPS-доступ (`APP_URL=https://…`). При HTTPS включается HSTS.
* **Роли базы:**
  * владелец схемы — отдельная роль без `SUPERUSER`;
  * приложение работает под ролью `ceh_app`, которая создаётся миграциями.
  На стенде сервер подключается суперпользователем. Проверка готовности показывает это как
  предупреждение; в эксплуатации так быть не должно.
* **Переменные окружения:**

  | Переменная | Значение |
  |---|---|
  | `DATABASE_URL` | подключение к базе |
  | `APP_URL` | адрес приложения |
  | `SMTP_URL`, `MAIL_FROM` | почта |
  | `BACKUP_DIR` | каталог резервных копий |
  | `ANTHROPIC_API_KEY` | ключ AI, необязателен |
  | `AI_MODEL` | модель AI, по умолчанию `claude-opus-5-5` |
  | `AI_DAILY_LIMIT` | дневной лимит запросов к AI, по умолчанию 300 |

  `DEV_MAILBOX` в эксплуатации **не задавать**.
* **Порядок первого запуска:**
  1. `npm run migrate`;
  2. `npm run import:reference` — справочник MON CHEF;
  3. `npm run import:ttk` — архив ТТК, 559 карт;
  4. `npm run build`, затем `npm start`;
  5. отдельным процессом `npm run mail:watch` — отправка писем.
* **Мониторинг:** `GET /api/v1/health` отвечает 200 и числом применённых миграций, или 503, если база недоступна.

## 3. Резервное копирование и восстановление (AT-16)

* **Ежедневно** (например, cron в 03:15): `npm run backup && npm run backup:verify`. Копию вместе с файлом `.json` рядом нужно класть вне сервера. Без успешной проверки восстановления копия резервной не считается.
* **`backup`** снимает дамп в одном снимке базы. Манифест из того же снимка содержит миграции с контрольными суммами, число строк каждой таблицы, состояние и последний хеш цепочки аудита каждой организации, таблицы с RLS и защитные триггеры.
* **`backup:verify`** восстанавливает копию во временную базу и сверяет:
  * контрольную сумму файла;
  * восстановление без ошибок;
  * миграции;
  * строки всех таблиц;
  * RLS;
  * триггеры;
  * цепочки аудита — пересчитываются заново и сравниваются с оригиналом.

  Временная база удаляется всегда. Повреждённый файл не проходит проверку (есть тест).
* **Восстановление после сбоя:**
  1. `createdb ceh_restored`;
  2. `pg_restore --exit-on-error --dbname=…/ceh_restored <файл.dump>`;
  3. переключить `DATABASE_URL` на восстановленную базу;
  4. запустить сервер;
  5. проверить `GET /api/v1/health` и экран «Готовность к пилоту»: цепочка аудита и проверки безопасности.

  Записи, сделанные после копии и до сбоя, переносятся с бумажных бланков с пометкой «внесено позже».

## 4. Если система недоступна

* Персонал ведёт бумажные бланки с реальным временем каждого действия. Бланки — печатные формы журналов из системы.
* После восстановления записи вносятся с реальным временем выполнения. Система пометит их «внесено позже». Записи старше суток внести нельзя — их хранят на бумаге и прикладывают сканом к отклонению как доказательство.
* Касса: при недоступности системы чеки пробиваются на ККТ как обычно. Продажи потом загружаются через «Продажи → Импорт продаж внешней кассы» с номерами чеков в качестве ID — повторов не будет.

## 5. Обучение

* **«Управление → Памятки по ролям»** — раздаточный лист для каждой роли: что делать каждую смену, что делать в типовых ситуациях, чего нельзя. Ваша роль открывается первой, страницу можно распечатать.
* **Инструктаж:** 30 минут на роль, на рабочем месте, по своей памятке. Каждый сотрудник делает свою операцию в системе при инструкторе: замер, приёмку, расход, оплату, запись в журнал. Факт инструктажа подтверждается в «Готовности к пилоту».
* Иллюстрированная инструкция по новой системе — `docs/ЦЕХ_инструкция_для_персонала.pdf` (36 страниц, снимки из демо-организации). Для инструктажа можно поднять демо-организацию: `npm run demo:seed`, вход и пароли — в `platform/README.md`. Инструкцию стоит пересобрать по итогам пилота.

## 6. Персональные данные (152-ФЗ, AT-15)

| Что хранится | Где | Зачем | Срок |
|---|---|---|---|
| Email, ФИО, хеш пароля | `users` | вход, подпись записей | пока есть учётная запись |
| Сессии: IP, устройство | `sessions` | безопасность входа, отзыв сессий | до истечения + журнал |
| Попытки входа: IP, email | `login_attempts` | защита от подбора пароля | определяет политика организации |
| Действия: кто, что, когда, IP | `audit_events` | неизменяемый журнал (ТЗ v2 §9) | по политике хранения журналов ХАССП |
| ФИО в записях журналов, отклонений, CAPA | таблицы операций | обязательные реквизиты записей пищевой безопасности | по срокам хранения журналов |
| Тексты вопросов к AI | `ai_jobs` | журнал AI (ТЗ v2 §11) | по политике организации |

* Пароли и токены хранятся только хешами — проверяется автоматически.
* Каждый пользователь может скачать сведения о себе: **«Управление → Мои данные»**. Выгрузка записывается в аудит.
* При вопросах к AI во внешний сервис уходят данные отклонения и тексты требований, ФИО сотрудников не передаются. Если AI подключён, это нужно отразить в политике обработки ПДн.
* Ответственного за ПДн, политику и согласия оформляет предприятие (Б-6). Факт подтверждается в «Готовности к пилоту».

## 7. Что смотреть во время пилота (2 недели)

| Показатель | Где | Ориентир |
|---|---|---|
| Пропущенные замеры | «Проблемы» | снижаются к концу первой недели |
| Отклонения: время до действия и до закрытия | «Проблемы», журнал J34 | нет открытых дольше смены |
| Продажи, не списанные по ТТК | «Продажи» | очередь разбирается ежедневно |
| Журналы подписаны | «Журналы» | еженедельно |
| Ответы AI, отклонённые проверкой | «Журнал AI» | разбирать каждый случай |
| Расхождения наличных в сменах | «Экономика» | разбирать каждое |
| Резервная копия проверена | «Готовность к пилоту» | ежедневно |

Итог пилота — решение о расширении по тем же проверкам, с перечнем найденных дефектов и решений по ним.

## 8. Результаты проверок на стенде (21.10.2026)

* **Автотесты:** 109, все проходят — этапы 1–8 и демо-организация, включая изоляцию организаций, неизменяемость записей, повторы операций, AI и резервное копирование.
* **Сквозные сценарии в браузере** — 10, все проходят: этапы 1–4, 5, 5b, 6, 6b, 7, 8.
* **Резервное копирование:** копия базы стенда 0,86 МБ, проверка восстановления 1,1 с. Совпали 63 таблицы, 20 защитных триггеров, 57 цепочек аудита.
* **Безопасность базы:** все критические проверки пройдены. Предупреждение одно — сервер стенда подключается суперпользователем.
* **Нагрузка** (`tests/load/smoke.mjs`): 20 параллельных клиентов, 20 секунд, смешанное чтение и запись, стенд на 4 ядрах.
  * **Первый прогон:** p95 = 1,4 с, предел не выдержан. Причина — журнал J01 строился 530 мс из-за полного перебора при поиске исправлений и связанных отклонений.
  * **Исправление:** добавлены индексы (миграция `011_performance_indexes.sql`). Журнал стал строиться ~75 мс.
  * **Повторный прогон:** 104 запроса в секунду, 0 ошибок, p95 по типам запросов от 287 до 580 мс при пределе 800 мс.
