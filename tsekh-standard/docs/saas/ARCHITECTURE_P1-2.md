# P1-2. Защита ядра и владение файлами клиента — решение и реализация

Собственность Слепцова Дениса Владимировича. Разработчик кода — Слепцов Денис Владимирович.

**Статус: реализовано в коде и проверено на модели Google Диска. Архитектура НЕ объявляется готовой до испытаний на двух реальных Google-аккаунтах (раздел 6).**

## 1. Решение
- Проект Apps Script каждого предприятия принадлежит поставщику и **не привязан** к таблице клиента (отдельный проект). Клиент не редактор проекта.
- Рабочее веб-приложение выполняется **от имени открывшего его Google-аккаунта** (`USER_ACCESSING`, доступ — вошедшим в Google). Файлы в «Моём диске» создаются с полномочиями клиента.
- Входят только Google-аккаунты предприятия: владелец (подтверждён при bootstrap) и список из CONTROL. Поверх — прежний вход по ПИН, роли, тариф.
- Служебное развёртывание того же проекта — **от имени поставщика, без входа в Google**: только датчики (`doPost`), QR-проверка подписи, портал проверяющего. Файлов не создаёт.
- CONTROL управляет кодом и версиями обоих развёртываний; клиентские данные и настройки при обновлении не затрагиваются.

Почему проект на каждое предприятие, а не один центральный: код хранит состояние в Script Properties (103 обращения) — они общие для всех пользователей проекта. Один проект на всех смешал бы состояние предприятий. Отдельный проект поставщика на предприятие сохраняет изоляцию свойств и централизованное управление релизами.

## 3. Критерии готовности

| № | Критерий | Модель (тесты) | Реальный Google |
|---|---|---|---|
| 1 | Клиент не имеет доступа к исходному коду | проект без привязки к таблице; в страницах браузера нет секретов, подписи лицензии, серверных сервисов, расчёты — на сервере (`ip_protection`) | не проверено |
| 2 | Документы клиента принадлежат клиенту | все объекты дерева предприятия В — владелец клиент (`tenant_isolation`, P1-2) | не проверено |
| 3 | Квота поставщика не расходуется | ни одного нового объекта поставщика | не проверено |
| 4 | CONTROL управляет релизами | два развёртывания, обновление без новых развёртываний | не проверено (Apps Script API) |
| 5 | Лицензирование — на сервере | без изменений (шлюз + CONTROL) | частично ранее |
| 6 | Нет данных другого предприятия | аккаунт Б не входит в систему В; у кода В нет прав на Диск А; границы дерева | не проверено |
| 7 | Отзыв доступа не уничтожает документы | клиент работает, документы на месте, у поставщика доступа нет | не проверено |
| 8 | Фоновые задачи в своей модели полномочий | включает владелец; расписание проходит шлюз по `triggerUid` при пустом `getActiveUser()` | не проверено |

## 4. Риски и открытые вопросы (по критичности)

1. **P0 для коммерческого запуска — проверка приложения в Google.** `DriveApp` требует полного доступа к Диску (`/auth/drive`) — это «ограниченная» область: для внешних пользователей нужна проверка приложения Google, а при определённых условиях ежегодная оценка безопасности (CASA). Без неё — экран «приложение не проверено» и ограничение числа пользователей. Варианты: (а) пройти проверку; (б) сузить права до `drive.file` (доступ только к файлам, созданным приложением) — требует переписать работу с Диском на расширенный сервис Drive API; (в) для клиентов на Google Workspace — администратор домена отмечает приложение доверенным. Нужно решение и уточнение условий по документации Google.
2. **Сотрудникам нужны Google-аккаунты и доступ к таблице.** Код выполняется от их имени, значит у аккаунта должны быть права редактора таблицы и папки предприятия — и он может открыть таблицу напрямую, минуя приложение. Смягчение: на устройствах кухни — один аккаунт предприятия (владелец), сотрудники различаются по ПИН; правки таблицы вручную видны в цепочке аудита и журнале правок. Выдачу доступа сотрудникам из приложения ещё нужно сделать.
3. **Служебное развёртывание работает от имени поставщика** (датчики, QR, проверяющий): если клиент отзовёт доступ поставщика, они перестанут работать (рабочее приложение — продолжит).
4. **Квоты Apps Script считаются по пользователю**: фоновые задачи и запросы расходуют квоты аккаунта клиента (у личных аккаунтов они меньше, чем у Workspace).
5. **Shared Drive (Workspace)** — отдельный адаптер ещё не сделан: `getOwner()` пуст, проверка владельца отмечает «недоступно» (WARN).
6. Предприятия, установленные в прежнем режиме (`USER_DEPLOYING`), при переходе имеют дерево с владельцем-поставщиком: проверка владельцев покажет FAIL; нужен перенос (копирование от имени клиента).

## 5. Тесты
`gate_security` (18, из них 4 — USER_ACCESSING), `tenant_isolation` (16, из них 5 — P1-2), `ip_protection`, все прежние наборы. Тест шлюза на прежнем коде падает — ловит P0.

## 6. Испытания на двух реальных аккаунтах (для владельца)
1. CONTROL под техническим аккаунтом поставщика; `MASTER_SCRIPT_ID` — проект-эталон. Два тестовых аккаунта клиентов (желательно один личный Gmail и один Workspace).
2. Bootstrap под каждым клиентом → «Предприятия 2.0 → Доступ»: режим USER_ACCESSING, аккаунт сотрудника → «Подготовить».
3. Проверить: в Google Drive клиента нет проекта; клиент не может открыть `script.google.com/d/<Script ID>` (нет доступа). Таблица клиента: «Расширения → Apps Script» создаёт **новый пустой** проект, а не код ЦЕХ Стандарт.
4. Клиент открывает рабочий адрес под своим аккаунтом → экран разрешений Google (записать, какой — «не проверено»?) → вход по ПИН.
5. Аккаунт другого клиента открывает этот адрес → «нет доступа».
6. Шаг 7 «Включить фоновые задачи» → в `script.google.com` → «Триггеры» под аккаунтом клиента видны задачи; дождаться часовой задачи.
7. Создать документ (ППК), архив месяца, резервную копию, фото, этикетку — в Диске клиента **у каждого файла владелец — клиент** (свойства файла). Проверить квоту поставщика до/после.
8. Проверка целостности (`ts4TenantIntegrityCheck`) → OWNERSHIP = PASS.
9. Датчик ESP32 на служебный адрес → показание принято; QR проверки подписи открывается без входа.
10. Выпустить релиз → обновить клиента → версия сменилась, данные, настройки и триггеры клиента на месте.
11. Клиент удаляет поставщика из доступа к папке → рабочее приложение работает, документы на месте; служебное (датчики) — перестаёт.
12. Клиент отзывает разрешения приложения (myaccount.google.com → Безопасность → сторонние приложения) → приложение запрашивает их снова; документы не удалены.

Источники ограничений: [веб-приложения Apps Script](https://developers.google.com/apps-script/guides/web), [манифест: webapp](https://developers.google.com/apps-script/manifest/web-app-api-executable), [проверка ограниченных областей OAuth](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification).
