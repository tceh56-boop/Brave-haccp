# Технический отчёт — ЦЕХ Стандарт SaaS, этап 4

## Результат
Этап 4 закрывает часть найденных рисков межклиентского доступа к файлам и создаёт диагностическую точку контроля tenant-хранилища. Основное правило: ID файла из таблицы или пользовательского запроса сам по себе не является доказательством принадлежности клиенту. Перед чтением/выдачей/копированием выполняется проверка пути в дереве текущего предприятия.

## Закрытые в коде сценарии
1. Чтение исходника документа из Drive вне `INBOX` через реестр `FILES`.
2. Чтение файла отката сверки из чужого/внешнего Drive.
3. Повторное использование ID месячного архива, не принадлежащего `ARCHIVE` клиента.
4. Игнорирование ошибки перемещения созданной архивной таблицы.
5. Выдача зарегистрированного файла через `getSecureFile()` без проверки tenant root.
6. Копирование в архив чужого исходного файла из реестра.
7. Использование подменённого ID фото-превью.
8. Утечка вновь созданной таблицы/документа в корень аккаунта поставщика при сбое `moveTo()` в ряде генераторов.
9. Экспорт PDF с использованием жёстко зашитого ID таблицы вместо активной tenant-конфигурации.

## Новая диагностика
Функция `ts4TenantIntegrityCheck(token)` доступна из клиентского Apps Script после добавления файла `TS4_TenantIntegrity.gs`. Она не изменяет Drive и не удаляет файлы. Возвращает PASS/FAIL по блокам:
- полнота внедрённой tenant-конфигурации;
- доступность клиентского корня и сверка владельца, если Google API возвращает owner;
- доступность таблицы, прямое размещение в корне и сверка владельца;
- логическое дерево папок и родительские связи;
- принадлежность файлов реестра `FILES` папке `INBOX` (до 500 записей за запуск);
- принадлежность резервных копий допустимым папкам (последние 200 записей).

## Важные ограничения и риски
- Никакие локальные тесты не доказывают фактическую изоляцию в Google Drive. Нужны два независимых клиентских аккаунта и попытки взаимного доступа к ID файлов, папок, таблиц, архивов, фото и резервных копий.
- `getOwner()` может быть недоступен для Shared Drives. Bootstrap сейчас намеренно требует подтверждённый email владельца, поэтому Shared Drives нужно отдельно проектировать и тестировать, а не считать уже поддержанными.
- Центральная нормативная база поставщика остаётся отдельным источником справочных данных; она не должна содержать клиентские операционные документы.
- Установка/обновление проекта через Apps Script API, фактическая выдача OAuth scopes, триггеры и web-app deployment не выполнялись.
- Необходимо отдельно провести восстановление из копии в тестовой организации и убедиться, что архивные файлы/манифесты/rollback-артефакты восстанавливаются полностью.

## Порядок проверки пилота
1. Создать две тестовые организации с разными Google-аккаунтами.
2. Выполнить bootstrap отдельно от имени каждого владельца.
3. Развернуть отдельные bound Apps Script проекты и проверить внедрённые `TS_TENANT_CONFIG_`.
4. Запустить `ts4TenantIntegrityCheck(token)` в обеих организациях; добиться PASS (для Shared Drive сценария запуск пока не использовать).
5. В организации A загрузить документ, фото, накладную, создать документ/форму, резервную копию и архив; проверить, что все ID находятся только в Drive A.
6. В организации B попытаться использовать ID файлов/папок A через доступные API и UI. Ожидаемый результат — отказ без выдачи содержимого и без изменения файлов A.
7. Повторить тест в обратном направлении.
8. Отключить у клиентского проекта доступ к корню клиента и проверить fail-closed: операции должны сообщать о недоступном хранилище, а не переключаться на Drive поставщика.
9. Проверить резервное восстановление, обновление релиза, блокировку/возврат лицензии и отзыв временного доступа поддержки.
10. Только после успешного протокола пилота переходить к платным клиентам.
