# ЦЕХ Стандарт SaaS — Этап 5: изоляция двух независимых предприятий

Собственность Слепцова Дениса Владимировича. Разработчик кода — Слепцов Денис Владимирович.

## 1. Название этапа
Этап 5. Полная изоляция двух предприятий (после проверки совместимости Stage 2, 3, 4).

## 2. Цель
Перенести накопительный пакет Stage 4 в актуальный код, проверить совместимость Stage 2–4 и подтвердить, что два предприятия не получают доступа к данным друг друга даже тогда, когда клиентский код работает от имени одного технического аккаунта поставщика.

## 3. Исходное состояние
- Актуальный код — ветка `claude/epic-newton-b1t9y3`, коммит `aa31947` (реестр нормативов в админ-панели).
- Пакет `ЦЕХ_Стандарт_SaaS_Stage4_Полный_патч.zip`: 20 клиентских файлов, 3 файла CONTROL, установщик `TS_TenantBootstrap.gs`, отчёты Stage 3–4.
- База пакета определена сравнением: все файлы Stage 4 построены от коммита `dc99f2c` (до реестра нормативов в админ-панели). Файлы CONTROL после этого менялись (`norms.registry`), поэтому пакет перенесён **трёхсторонним слиянием** (база `dc99f2c` → текущий код + Stage 4), а не копированием поверх.
- Результат слияния: 19 клиентских файлов и 2 файла CONTROL — без конфликтов; 1 конфликт (`admin/API.gs`: обе версии добавили своё действие в один список) — разрешён, оставлены оба (`norms.registry`, `tenant.bootstrap`).

## 4–5. Обнаруженные проблемы и критичность

| № | Проблема | Критичность | Статус |
|---|---|---|---|
| P0-1 | Bootstrap (Stage 2) подписывает запрос по схеме v2 (`HMAC(key|ts|тело)`), CONTROL проверял только v1 (`HMAC(key|ts)`). Регистрация клиентского хранилища **всегда** отклонялась («Подпись запроса не принята») — установка Stage 2–4 не могла пройти. | P0 | исправлено |
| P1-1 | `_ts2Ent_()` брал ID предприятия сначала из листа `SYSTEM_CONFIG` таблицы, затем из конфигурации, внедрённой CONTROL. Скопированная или изменённая таблица могла выдать проект за другое предприятие. | P1 | исправлено (fail-closed) |
| P1-2 | **Владелец файлов.** Клиентский код выполняется от имени аккаунта поставщика (`executeAs: USER_DEPLOYING`). В «Моём диске» Google владелец нового файла — тот, кто его создал: подпапки дерева, документы, PDF, архивы, создаваемые системой в папке клиента, принадлежат поставщику (в модели — 24 объекта на двух предприятиях). Расположение изолировано (всё внутри Диска клиента), но владение — нет: квота поставщика, при отзыве доступа файлы остаются за поставщиком. | P1 | **не исправлено — нужно решение владельца продукта** (варианты ниже) |
| P2-1 | Отказы изоляции (`TENANT_ISOLATION`, `TENANT_OWNERSHIP`) CONTROL возвращал как «internal error» и не записывал как событие безопасности. | P2 | исправлено |
| P2-2 | Обновление клиента без подтверждённого хранилища заблокировано (Stage 3). Установки, сделанные прежним установщиком (одна таблица, без tenant-корня), обновить нельзя до миграции. Сейчас таких клиентов нет. | P2 | принято; миграция — отдельный этап |
| P2-3 | В legacy-режиме (без tenant) остаются фиксированные ID папок исходной установки MonChef (`PHOTO_FOLDER_ID`, `TTK_FOLDER_ID`, `BLANKS_FOLDER_ID` …) как запасной путь. В tenant-режиме не используются. | P2 | оставлено до миграции |
| P3-1 | Shared Drives (Google Workspace) не поддержаны: `getOwner()` пуст, bootstrap и CONTROL намеренно отклоняют. | P3 | ограничение |

### P1-2: варианты решения (нужно решение)
1. **Google Workspace: общий диск (Shared Drive) на каждого клиента.** Владелец всех файлов — общий диск клиента, поставщик — участник с ролью. Правильный вариант для бизнес-клиентов; требует режима Shared Drive (проверка членства вместо `getOwner()`).
2. **Веб-приложение клиента выполняется от имени клиента** (проект и развёртывание создаёт клиент, поставщик — редактор проекта). Файлы принадлежат клиенту. Нужно проверить на реальных аккаунтах, что CONTROL может обновлять код и версию развёртывания, не меняя «от чьего имени».
3. **Оставить как есть и закрепить в договоре**: поставщик — владелец служебных файлов, при завершении обслуживания — передача владельца (в личных аккаунтах Google требует согласия получателя) или выгрузка копии.

## Сценарий проверки на реальных аккаунтах (для владельца)
1. Два тестовых Google-аккаунта клиентов (A, B) и технический аккаунт поставщика. CONTROL развёрнут под поставщиком.
2. В CONTROL: две организации, лицензии. Сохранить ключ и секрет каждой.
3. Под аккаунтом A: новый проект Apps Script → `installer/TS_TenantBootstrap.gs` → заполнить 5 полей → `tsTenantBootstrapStart()`. Ожидаем: папка и таблица на Диске A, поставщик — редактор, в CONTROL у организации A заполнены `Customer Drive Root ID`, `Google Drive ID`, `Customer Drive Owner Email`.
4. То же под аккаунтом B.
5. В CONTROL: «Предприятия 2.0 → Подготовить» для A и B. Ожидаем: шаги DONE; в проектах A и B `TS_TENANT_CONFIG_` с разными корнями.
6. Попытка: в CONTROL вписать организации B корень A → отказ `TENANT_ISOLATION`.
7. В системе A: «Проверка целостности» (`ts4TenantIntegrityCheck`) → PASS. Создать документ, архив, фото — все в дереве A. Записать, **кто владелец** созданных файлов (P1-2).
8. Аккаунт A убирает поставщика из редакторов папки → операции A завершаются отказом, у поставщика не появляется своих папок; B работает.
9. Вернуть доступ → A снова работает без потери данных.
