# ЦЕХ — платформа (ТЗ v1/v2)

Единая система управления общепитом. Решение владельца: новая платформа по ТЗ — TypeScript (Next.js)
и PostgreSQL. Механика MON CHEF и функции прежнего ЦЕХ переносятся как бизнес-правила по описям
(`docs/ЭТАП_0_АУДИТ.md`, `docs/ОПИСЬ_ЦЕХ.md`, `monchef/docs/ОПИСЬ_MON_CHEF.md`).

## Устройство

| Слой | Где | Правило |
|---|---|---|
| Интерфейс | `src/app` (страницы), `src/components` | рассчитан в первую очередь на телефон; бизнес-правил в интерфейсе нет |
| API v1 | `src/app/api/v1/**/route.ts` → `src/server/http/route.ts` | единый ответ `{ ok, data \| error }`; сессия в cookie (httpOnly); изменяющий запрос с чужого сайта отклоняется |
| Предметные модули | `src/server/<домен>` | проверка прав роли на сервере для каждого действия и площадки (`access/guard.ts`) |
| База | `migrations/NNN_*.sql`, `src/server/db` | Row-Level Security: приложение работает под ролью `ceh_app`, строки чужой организации база не отдаёт |
| Аудит | `audit_events` | только дописывание, цепочка SHA-256 на организацию, правка и удаление запрещены триггером |

## Запуск

```
# PostgreSQL 16; базы ceh_dev и ceh_test
export DATABASE_URL=postgres://ceh@localhost:54329/ceh_dev APP_URL=http://localhost:3000
npm install --legacy-peer-deps
npm run migrate
npm run build && npm start         # или npm run dev
npm test                           # тесты на чистой базе ceh_test (TEST_DATABASE_URL)
BASE_URL=http://localhost:3000 node tests/e2e/stage1.e2e.mjs   # сквозной сценарий в браузере
```

Письма (подтверждение, восстановление, приглашения) кладутся в очередь `outbox_emails`. Отправка через
SMTP подключается при развёртывании. Для стенда есть `GET /api/v1/dev/outbox` при `DEV_MAILBOX=1`
вне рабочей среды.

## Этап 1 (ТЗ v2 §15): организации, пользователи, роли, изоляция, аудит, миграции — готов

* **Учётные записи:**
  * регистрация по email с подтверждением;
  * вход;
  * выход;
  * восстановление пароля, которое закрывает все сессии;
  * блокировка на 15 минут после 5 неверных паролей;
  * ограничение неудачных попыток с одного адреса;
  * пароли хранятся хешем scrypt, ссылки и сессии — хешем токена.
* **Организации и площадки:**
  * владелец создаёт предприятие только с подтверждённым email (ТЗ v1 AT-01);
  * статусы DRAFT / CONFIGURED / COMPLIANCE_REVIEW, соответствие автоматически не выставляется.
* **11 ролей ТЗ v1 §4:**
  * права проверяются на сервере;
  * доступ ограничивается площадками;
  * кто кого может назначать: HR не назначает администратора;
  * последнего владельца нельзя снять;
  * менять самого себя нельзя.
* **Приглашения:**
  * по email, на 7 дней, отзыв;
  * принимаются только тем же подтверждённым адресом.
* **Увольнение:** блокировка с причиной; доступ закрывается сразу, история сохраняется.
* **Аудит:**
  * «было / стало», отказы в доступе пишутся отдельно;
  * проверка цепочки, подмена обнаруживается;
  * пароли и токены в аудит не попадают.

* Сквозной сценарий в браузере на экране телефона (`tests/e2e/stage1.e2e.mjs`).

## Этап 2 (ТЗ v2 §15): экран сотрудника и дашборд проблем — готов

* **Смена** (`/app/<орг>/shift`). Крупные плитки: «Приёмка», «Температура», «Сроки», «Задачи», «Проблемы»,
  «Сообщить». Ниже — объекты контроля с состоянием по графику («в норме», «пора замерить»,
  «пропущен замер»). Внизу экрана — меню.
* **Температура:**
  * предел, частота и основание берутся только из утверждённого правила. Проект правила не применяется;
    без правила замер сохраняется как «критерий не задан», без оценки;
  * время измерения хранится отдельно от времени внесения. Ввод позже 15 минут помечается и требует
    пояснения, старше суток — запрещён;
  * замер не изменяется и не удаляется, исправление — новая запись с причиной.
* **Отклонение:**
  * при отклонении создаются инцидент, задача ответственному и уведомления. Повтор не плодит дубли,
    нормальный повторный замер отклонение сам не закрывает;
  * карточка показывает основание, утверждённые шаги реакции и затронутые партии;
  * изолировать продукцию можно, только если это разрешает процедура;
  * порядок: Новая → В работе → Ожидает проверки → Закрыта. Закрытие подтверждает другой ответственный;
    без записанного действия закрыть нельзя, в том числе прямым запросом к базе.
* **Приёмка** одной операцией:
  * принять можно только при пройденных проверках: упаковка, маркировка, документы, качество. Иначе —
    карантин или отказ с причиной; товар с истёкшим сроком принять нельзя;
  * при завершении создаются партии; для партии без срока — «Срок не подтверждён» и задача;
    для карантина — отклонение и задача решения.
* **Сроки:**
  * статусы «В норме», «Скоро истекает», «Истёк», «Срок не подтверждён»; срок принимается только
    с основанием;
  * просроченная партия блокируется с отклонением. Карантинная, просроченная и без подтверждённого срока
    не используются (`assertLotUsable`).
* **Дашборд проблем:**
  * приоритеты §2: критично → просрочено/карантин → вне предела → приёмка → пропущенный замер →
    просроченная задача → предупреждения;
  * каждая карточка ведёт на конкретный объект и действие.
* **Настройка** (`/setup`): объекты контроля, правила (проект → утверждение, история версий), товары,
  поставщики.

Проверки:
* 30 тестов (`tests/stage1.test.ts`, `tests/stage2.test.ts`), в том числе AT-01…AT-06 и AT-11 ТЗ v2;
* сквозной сценарий в браузере (`tests/e2e/stage2.e2e.mjs`): настройка → приёмка → отклонение →
  дашборд → действие с изоляцией → подтверждение другим ответственным → сроки.

Ещё не сделано в этапе 2: сканирование QR/штрихкода камерой (код объекта для наклейки уже есть),
приём показаний с датчиков, доставка уведомлений по email/Telegram (сейчас — лента в приложении).

## Этап 3 (ТЗ v2 §15): склад, FEFO, списания, прослеживаемость, единый каталог — готов

* **Справочник MON CHEF.**
  * 1549 ProductID загружаются командой `npm run import:reference` (`data/reference/monchef_catalog_v55.json`);
  * каждая исходная строка — отдельная запись: 88 групп одинаковых названий помечены и не сливаются;
  * повторная загрузка не дублирует записи и не сбрасывает статус проверки;
  * пищевая ценность и сроки — справочные, со статусом «на проверке»;
  * товар предприятия создаётся из справочника или привязывается к нему решением человека.
* **Журнал движений.**
  * приход, расход, списание, перемещение, инвентаризация;
  * журнал нельзя изменить или удалить, остаток партии меняется только движением.
* **Расход по FEFO** — единственный путь расхода, механика MON CHEF:
  * партии берутся по ближайшему сроку; карантинные, просроченные и без подтверждённого срока
    не участвуют;
  * в минус не уходит: при нехватке операция отклоняется с указанием доступного количества;
  * выбор другой партии — только с причиной, движение помечается «не по FEFO».
* **Защита от повтора** (ТЗ v2 AT-12): операция с тем же ключом не проводится второй раз и возвращает
  прежний результат.
* **Единицы** пересчитываются только по подтверждённому коэффициенту с основанием (ТЗ v1 §6, AT-06).
* **Списание по причинам.**
  * доступно и для просроченных, и для карантинных партий;
  * «Другое» — только с описанием;
  * связанные задачи закрываются, отклонение получает запись о факте списания.
* **Перемещение** на другую площадку: дочерняя партия с тем же сроком и основанием. Карантинные
  не перемещаются.
* **Прослеживаемость** (AT-13):
  * назад — поставщик, документ, приёмка, путь по площадкам;
  * вперёд — движения и дочерние партии;
  * все партии поставщика — для проверки и отзыва.
* **Инвентаризация.** Ожидаемые остатки фиксируются при начале. Закрыть можно только после подсчёта
  всех строк; расхождения проводятся корректирующими движениями «недостача / излишек».

Проверки:
* 41 тест (`tests/stage1..3.test.ts`);
* сквозной сценарий в браузере (`tests/e2e/stage3.e2e.mjs`): товар из справочника → приёмка →
  расход по FEFO → перемещение → списание → прослеживаемость → инвентаризация.

## Этап 4 (ТЗ v2 §15): нормативный реестр — готов

* **Источник и редакции.**
  * у источника: обозначение, вид, официальное название, издатель, URL, юрисдикция, обязательность;
  * у редакции: даты публикации, начала и окончания действия, переходные положения, где и как проверено,
    кто проверил, следующая проверка, владелец актуализации;
  * у пункта: формулировка из официального текста, область применения, процессы и типы объектов.
* **Статусы ТЗ v2 §7.**
  * порядок работы: «Проект» → «Требует проверки» → «Проверен специалистом» → утверждение;
  * «Скоро вступает в силу», «Действует», «Утратил силу» система вычисляет из дат. Заменённая редакция
    становится «Утратил силу» с даты вступления новой;
  * «Приостановлен / оспаривается» — с основанием.
* **AT-08.** Утверждение только для проверенной редакции с датой начала действия, хотя бы одним пунктом,
  владельцем и датой следующей проверки. Иначе — понятный список причин. Утверждённая редакция не правится.
  Правка проверенной возвращает её на проверку.
* **Стартовый перечень ТЗ v2 §8** загружается кнопкой. Все записи — «Требует проверки». Пункты и даты,
  которых нет в ТЗ, не заполнены. Для СанПиН 2.3/2.4.4282-26 даты взяты из ТЗ с пометкой «требует сверки».
* **AT-09.** Новая редакция копирует пункты в черновик. При утверждении:
  * сравнивает пункты: добавлены, исключены, изменены;
  * правила контроля по неизменённым пунктам переходит на новую редакцию сам;
  * по изменённым и исключённым пунктам ставит задачи «Пересмотреть правило контроля».
* **Нормативный профиль предприятия.**
  * тип объекта и процессы; система предлагает применимость каждого пункта, решает специалист с обоснованием;
  * подсвечиваются применимые требования без процедуры контроля.
* **Требование → правило контроля.** Правило на объекте ссылается на применимый пункт действующей или
  вступающей редакции, основание подставляется: «ПК-03, п. 2 (ред. …)».
* **Дашборд** показывает «Пора проверить актуальность», когда наступила дата следующей проверки.
* **Права:** просмотр — специалисты и аудитор; ведение и проверка — ответственный ХАССП и технолог;
  утверждение — владелец, администратор, директор.

## Этап 5, часть 1 (ТЗ v2 §15): журналы J01–J53 из событий — готов

* **Одна операция → все формы.** 53 формы из книги «Журналы_J01-J53» (`data/reference/journal_forms.json`).
  Из операций смены собираются:
  * замеры холодильников — J01, J25 и месячная сетка J42;
  * помещения — J04 и сетка J43;
  * приёмка — J03, J21, J39;
  * партии, сроки, FIFO — J05, J29;
  * отклонения и корректирующие действия — J34.
  Вносить строку в эти журналы вручную нельзя — вносится сама операция.
* **Ручные формы** ведутся записью по столбцам шаблона. Пара пересекающихся форм (J02 ↔ J40, J38 ↔ J41 …)
  хранит одни записи. Сводные формы (J44, J50, J53, J10) ведутся своими записями — разные журналы по цепочке
  не склеиваются.
* **Запись неизменяема (AT-11).**
  * время выполнения хранится отдельно от времени внесения;
  * позже 15 минут — пометка «внесено позже», старше суток и в будущем — нельзя;
  * исправление — новой записью с причиной, исходная остаётся.
* **Подпись за период** хранит SHA-256 содержимого.
  * подписать нельзя при открытых отклонениях периода;
  * изменение после подписи видно: «Журнал изменился после подписи»;
  * подпись не правится и не удаляется.
* **Выгрузка:** CSV для Excel (BOM, «;»), печатная форма A4 с шапкой предприятия, подписью и контрольной суммой.
* **Права:** просмотр и ручная запись — персонал смены; подпись — директор, шеф и ответственный ХАССП.

## Этап 5, часть 2: план ХАССП, CAPA, доказательства, пакет для проверки — готов

* **План ХАССП (ТЗ v1 §10)** — версии: «Проект» → «Утверждён» → «Заменён».
  * этапы процесса с подтверждением на месте (кто, когда, как); изменение этапа снимает подтверждение;
  * опасности по этапам (биологические, химические, физические, аллергены …), вероятность и тяжесть 1–3.
    «Не оценено» не равно нулю; матрица рисков 3×3;
  * дерево решений (Кодекс Алиментариус): система только предлагает «ККТ / не ККТ / изменить этап».
    Класс ПРП / ОПРП / ККТ назначает человек с обоснованием. Если решение расходится с предложением,
    нужно подробное обоснование. Изменение оценки или мер снимает класс;
  * мониторинг для ОПРП и ККТ: что, где, как, частота, предел, прибор, ответственный, журнал, реакция.
    Можно связать с правилом контроля объекта — тогда предел берётся из утверждённого правила;
  * утверждение (владелец, администратор, директор) — только без препятствий:
    * этапы подтверждены;
    * у опасностей есть оценка, меры и класс;
    * у ККТ есть критический предел;
    * связанное правило утверждено;
  * утверждённую версию нельзя править ни через систему, ни напрямую в базе (триггеры).
    Новая версия копирует утверждённую и требует причины.
* **Журналы J30–J32** собираются из плана: реестр версий, анализ опасностей, план ХАССП.
* **CAPA.**
  * отклонение высокого и критического риска после закрытия открывает CAPA автоматически.
    Можно открыть и вручную — из отклонения или самостоятельно;
  * порядок: причина → корректирующее и предупреждающее действие → критерий эффективности →
    ответственный и сроки → «выполнено» → проверка эффективности;
  * эффективность проверяет другой человек. Если неэффективно — CAPA снова в работе с задачей;
  * закрыть без проверки нельзя (ограничение в базе); история неизменяема;
  * причина и меры CAPA попадают в J34.
* **Доказательства.**
  * фото (JPEG, PNG, WebP, HEIC) и PDF до 10 МБ к отклонению, CAPA, приёмке, партии, замеру,
    этапу и опасности ХАССП, записи журнала, редакции норматива;
  * тип определяется по содержимому, хранится SHA-256, повторная загрузка того же файла не создаёт дубль;
  * файл нельзя удалить или заменить;
  * просмотр отдаётся без исполнения содержимого.
* **Пакет для проверки** — ZIP за период по площадке, собирается без внешних библиотек:
  * сводка `index.html`;
  * журналы (печатный вид и CSV) с отметкой о подписи;
  * план ХАССП;
  * отклонения и CAPA;
  * применимые требования;
  * доказательства;
  * `checksums.sha256`.
  Формулировка о соответствии — допустимая по ТЗ v2 §16. Выгрузка записывается в аудит.
* **Права:**

  | Действие | Кто |
  |---|---|
  | Ведение плана ХАССП | технолог, ответственный ХАССП |
  | Ведение CAPA | технолог, ответственный ХАССП, шеф |
  | Проверка эффективности CAPA | ответственный ХАССП, шеф, директор |
  | Доказательства | весь персонал смены |
  | Пакет для проверки | ответственный ХАССП, руководители, аудитор |

## Этап 6, часть 1: блюда, ТТК, себестоимость, КБЖУ, архив карт — готов

* **Блюда и полуфабрикаты.** Цену продажи ставят руководитель, шеф или бухгалтер-экономист. Сотрудник цеха
  видит состав и технологию, но не цены и не себестоимость.
* **ТТК с версиями:** «Черновик» → «На согласовании» → «Утверждена» → «Архив».
  * отправить и утвердить можно только без препятствий:
    * технология, условия хранения, срок по основанию, выход (и порция для блюда);
    * всё сырьё сопоставлено; нетто не больше брутто;
    * у полуфабриката есть утверждённая ТТК;
    * есть коэффициент единиц для списания со склада;
  * утверждает человек с правом (шеф, технолог, руководитель); можно вернуть на доработку с замечанием;
  * утверждённую и архивную версию нельзя изменить ни через систему, ни напрямую в базе;
  * новая версия копирует утверждённую и требует причины; утверждённая действует до утверждения новой;
  * при утверждённом плане ХАССП новая ТТК ставит ответственному задачу проверить план.
* **Себестоимость** считается по ценам партий из приёмки (новое поле «Цена за единицу»):
  * цена — средневзвешенная по остатку, иначе последняя закупка;
  * полуфабрикат — по его утверждённой ТТК;
  * нет цены или коэффициента — себестоимость «неполная» со списком причин, а не заниженная;
  * на порцию, на 1 кг выхода, фудкост от цены продажи.
* **КБЖУ на 100 г** — из справочника MON CHEF по закладке нетто, с вложенными полуфабрикатами.
  Помечается как ориентировочное: без потерь при тепловой обработке, справочник не проверен (Б-5).
  Если данных нет ни у одного ингредиента — «не рассчитано», а не 0.
* **Архив ТТК — 559 карт** (`data/reference/ttk_archive.json`, загрузка `npm run import:ttk`):
  * поиск по разделам, просмотр карты с замечаниями разбора;
  * импорт выбранных карт черновиками; повторный импорт не создаёт дублей;
  * п/ф распознаются как полуфабрикаты.
* **Сопоставление сырья — один раз на название.** Сопоставили «Хрен сливочный» с товаром — применилось
  во всех черновиках и подставляется при следующих импортах. Можно сразу создать товар из названия.

## Этап 6, часть 2: касса, продажи, стоп-лист, экономика — готов

Механика модуля «Касса и зал» прежнего ЦЕХ (`Pos.gs`), перенесённая на платформу. Фискальный чек пробивает ККТ
предприятия (ТЗ v2 §10): система её не заменяет.

* **Смена.**
  * открывается с суммой наличных на начало; одна смена на площадку;
  * X-отчёт считается по оплатам: наличные, карта, прочее, возвраты, средний чек, ожидаемые наличные;
  * закрыть нельзя, пока есть неоплаченные заказы; фактические наличные вводятся при закрытии,
    расхождение фиксируется как есть.
* **Заказ.**
  * цена берётся из карточки блюда на сервере; одинаковые позиции суммируются;
  * есть защита от одновременной правки с двух устройств (версия заказа);
  * блюдо из стоп-листа добавить нельзя; отмена неоплаченного — с причиной.
* **Оплата.**
  * наличные, карта, прочее или смешанная оплата; безнал — не больше суммы, сдача — только с наличных;
  * повтор с тем же ключом операции возвращает первый результат, второй оплаты нет (AT-12);
  * оплаты не правятся и не удаляются (триггер).
* **Возврат** — право руководителя.
  * полный или по позициям, в открытой смене;
  * безналом — не больше, чем им оплачено;
  * отрицательная оплата и отрицательная продажа; сырьё на склад не возвращается.
* **Продажа → списание по утверждённой ТТК через FEFO.**
  * вложенные полуфабрикаты разворачиваются до сырья;
  * себестоимость считается по ценам списанных партий;
  * если списать нельзя (нет ТТК, не хватает годного остатка), оплата не срывается: продажа уходит в
    очередь с причиной, шеф получает одну задачу на блюдо;
  * «Повторить списание» после исправления закрывает задачу.
* **Стоп-лист.**
  * автоматический: из годного остатка по утверждённой ТТК не собрать ни одной порции; в причине —
    какого сырья не хватает и сколько нужно на порцию; снимается сам, когда сырьё пришло;
  * без ТТК автоматический стоп не ставится;
  * ручной стоп ставят шеф или руководитель, с причиной;
  * при остатке меньше 5 порций касса предупреждает «осталось N».
* **Импорт продаж внешней кассы** (iiko, r_keeper, другая) — CSV `ID;дата;наименование;количество;цена`:
  * ID строки уникален, поэтому повторная загрузка не дублирует продажи;
  * неизвестное название уходит в очередь сопоставления; сопоставили один раз — все такие продажи
    сразу списываются.
* **Экономика за период** по площадке или всем:
  * выручка (касса и импорт, возвраты минусом), заказы, средний чек, оплаты по способам;
  * себестоимость фактически списанного, фудкост, маржа, списания сырья, блюда, смены с расхождениями;
  * продажи без списания или без цен партий делают маржу «неполной» со счётчиком, а не нулевой.
* **Роль «Кассир / официант»:** касса без доступа к складу, ценам закупки и экономике.

Проверки этапа 6, часть 2: тесты `tests/stage6b.test.ts`, сквозной сценарий `tests/e2e/stage6b.e2e.mjs`.

## Этап 7: AI-помощник с цитированием и подтверждением человеком — готов

ТЗ v2 §11 и AT-07. Модель — Claude Opus 5.5 (`claude-opus-5-5`) через официальный SDK `@anthropic-ai/sdk`:
* структурированный ответ по схеме;
* серверный резерв при отказе модели (`fallbacks: "default"`);
* `effort: high`, кэш системной инструкции.

Ключ — `ANTHROPIC_API_KEY`. Без него AI не вызывается, а поиск по реестру работает. Модель меняется через
`AI_MODEL`, дневной лимит запросов — через `AI_DAILY_LIMIT` (по умолчанию 300). `AI_PROVIDER=off`
выключает AI.

* **Источники ищет система, а не модель.** Ищутся только требования утверждённых редакций (действующих
  или вступающих в силу), признанные применимыми. Проекты и редакции «Требует проверки» AI не видит.
  Для отклонения первым берётся требование, на которое ссылается правило объекта.
* **Формат ответа по ТЗ:** что обнаружено → почему важно → что сделать сейчас → что нельзя до решения →
  кто подтверждает → что закроет проблему → источник → ограничения и уверенность.
* **Реквизиты каждой цитаты (AT-07):** источник, пункт, редакция, статус, дата проверки и следующей
  проверки, дословная цитата.
* **Сервер проверяет ответ.**
  * цитата должна дословно совпадать с текстом источника, иначе она отбрасывается и показывается как
    недостоверная;
  * любое число с единицей (°C, минуты, часы, сутки, %, граммы, литры) должно встречаться во входных
    данных или источниках; даты и идентификаторы числа не подтверждают;
  * если проверка не пройдена, ответ не показывается — «Ответ отклонён проверкой».
* **Нет требования в реестре** — модель не вызывается: «AI не отвечает без источника».
* **Решает человек.**
  * предложенное действие становится задачей только по кнопке «В задачу», с выбором исполнителя;
  * отказ — с причиной; одно решение на действие;
  * по отклонённому ответу задач не создать.
* **Журнал AI неизменяем.** Хранит: кто и что спросил, снимок данных, переданных модели, источники,
  модель и версию инструкции, статус, ответ, итог проверки, время, решения людей. Руководитель и
  аудитор видят весь журнал, сотрудник — свои запросы.
* **Где используется:**
  * экран «AI-помощник» — вопрос по требованиям;
  * карточка отклонения — «Объяснить с AI и подсказать, что делать»;
  * карточка CAPA — «Предложить причины и действия»;
  * журнал AI.

Проверки:
* 99 тестов, AI — на тестовом провайдере: формат, цитаты, отклонение чисел без источника, отказ модели,
  отсутствие источника, решения, журнал, изоляция;
* сквозные сценарии `tests/e2e/stage1..7.e2e.mjs`, `stage5b`, `stage6b`. Сценарий этапа 7 проходит без
  ключа AI: поиск по реестру, реквизиты цитат, журнал.
