# Архитектура: модуль «Касса и зал» для ЦЕХ

Источник: `replica/recon.md`, `replica/features.csv`. Объём первой очереди (решение владельца, 2026-10-06):
**касса + приложение официанта + зал/столы + модификаторы + стоп-лист + смены + автосписание по ТТК.
Без фискализации** — чеки пока пробивает текущая ККТ заведения.

## 1. Стек — не меняем

| слой | выбор | почему |
| --- | --- | --- |
| сервер | Google Apps Script, новый файл `gas/Pos.gs` | весь ЦЕХ уже на GAS; одна кодовая база, одни права, один аудит |
| БД | Google Sheets через `CONFIG.SHEETS` / `CONFIG.SCHEMA` и `insertRow_/findOne_/updateRow_` | тот же слой данных, что у 100+ существующих модулей |
| API | новые действия в `processOperation` (`API.gs`), права через `ACTION_MODULE` / `ROLE_MODULES` | готовые сессии, RBAC, идемпотентность (`Idempotency.gs`), каскады, `AUDIT_LOG` |
| UI | новые разделы в `gas/Index.html` (SPA), токены ЦЕХ | дизайн-система ЦЕХ; официант — та же страница в мобильной вёрстке |
| фоновые задачи | задача в существующем 15-минутном диспетчере `TriggerScheduler.gs` | лимит 20 триггеров уже почти выбран — новых триггеров не добавляем |
| списание | существующие `createSale_` + `fulfillSaleByTtk_` (`SaleFulfillment.gs`) | FIFO по партиям, брутто/нетто, отходы, прослеживаемость, журналы HACCP — уже есть |

Соглашения проекта сохраняем: деньги в рублях с `round2_` (а не в копейках, как в шаблоне скилла) — так
считает весь ЦЕХ; даты `nowIso_()`; все записи — с `organization_id`, `location_id`, `cascade_id`.

## 2. Схема (новые листы)

Добавляется в `CONFIG.SHEETS`, `CONFIG.SCHEMA` и префиксы ID (рядом с `SALES: 'SALE'`).

```js
// CONFIG.SCHEMA — модуль «Касса» (Pos.gs)
POS_HALLS:        ['hall_id','organization_id','location_id','название','порядок','статус','создано'],
POS_TABLES:       ['table_id','organization_id','location_id','hall_id','название','мест','порядок','статус','создано'],
                  // статус: активен | архив. Занятость НЕ хранится — вычисляется из открытых заказов.
MODIFIER_GROUPS:  ['group_id','organization_id','название','мин','макс','обязательная','статус','создано'],
MODIFIERS:        ['modifier_id','organization_id','group_id','название','цена_delta',
                   'product_id','расход_qty','единица','статус','создано'],
                  // product_id/расход_qty — необязательно: «двойной сыр» списывает продукт со склада.
DISH_MODIFIER_LINKS: ['link_id','organization_id','dish_id','group_id','порядок'],
POS_SHIFTS:       ['shift_id','organization_id','location_id','кассир_id','открыта','закрыта',
                   'нал_начало','нал_конец_факт','итог_нал','итог_карта','итог_прочее',
                   'заказов','возвратов_сумма','статус','cascade_id'],
                  // статус: открыта | закрыта. Не более одной открытой смены на точку.
POS_ORDERS:       ['order_id','organization_id','location_id','shift_id','table_id','официант_id',
                   'номер','гостей','статус','сумма','скидка','итого','комментарий',
                   'version','создано','обновлено','оплачен','cascade_id'],
                  // статус: открыт | пречек | оплачен | отменён | возврат
                  // version — оптимистичная блокировка: два официанта на одном столе.
POS_ORDER_LINES:  ['line_id','order_id','organization_id','dish_id','название_снимок','qty',
                   'цена','модификаторы_json','сумма','статус','на_кухню_в','sale_ids','создано'],
                  // статус: новая | на_кухне | отменена. sale_ids — ссылки на SALES после оплаты.
POS_PAYMENTS:     ['payment_id','order_id','organization_id','location_id','shift_id','способ',
                   'сумма','operation_id','создано','user_id'],
                  // способ: нал | карта | прочее. operation_id — защита от двойной оплаты.
STOP_LIST:        ['stop_id','organization_id','location_id','dish_id','причина','источник',
                   'создано','снято','user_id'],
                  // источник: ручной | авто_остатки. Активен, пока «снято» пусто.
```

Связи и правила целостности (проверяются в `Pos.gs` под `withLock_`, т.к. в Sheets нет FK):
- `POS_ORDERS.table_id` → `POS_TABLES`; на столе не больше **одного** заказа в статусе `открыт|пречек`.
- `POS_ORDER_LINES.dish_id` → `DISHES` той же организации (`assertOwnedByOrg_`), блюдо не `архив`, не в стоп-листе.
- Заказ можно создать только при открытой смене на точке; смену нельзя закрыть с открытыми заказами.
- Оплаченный заказ неизменяем; исправление — только возвратом (новые строки, история не переписывается —
  принцип ЦЕХ, как в `WRITE_OFFS`/`AUDIT_LOG`).
- Сумма считается **на сервере** из `DISHES.цена_продажи` + `MODIFIERS.цена_delta`; клиентские суммы игнорируются.

| `POS_GET_SHIFT` | текущая смена и X-отчёт | pos_shift | — | F04 |
| `POS_CLOSE_SHIFT` | Z-отчёт, сверка нала, передача в «Экономику» | pos_shift | cashFact | F04 |
| `POS_CREATE_ORDER` | новый заказ (стол или «с собой») | pos, pos_waiter | tableId?, guests | F01, F02 |

| `POS_PRECHECK` | пречек (заказ заблокирован для официанта) | pos, pos_waiter | orderId | F02 |
| `POS_PAY` | оплата (одним или несколькими способами), создание SALES, постановка на списание | pos | orderId, payments[], operationId | F01 |
| `POS_CANCEL_ORDER` | отмена неоплаченного заказа, с причиной | pos_admin | orderId, reason | — |
| `POS_REFUND` | возврат оплаченного (полный/по позициям), сторно в SALES | pos_admin | orderId, lineIds?, operationId | — |
| `POS_MOVE_ORDER` | перенос на другой стол | pos, pos_waiter | orderId, tableId | F02 |
| `POS_GET_ORDERS` | список заказов смены/дня с фильтрами | pos, pos_admin | filters | — |
| `POS_GET_KITCHEN_QUEUE` | позиции `на_кухне` по цехам (`DISHES` → цех ТТК) | pos_kitchen | workshopId? | F02 |
| `POS_SET_STOP` / `POS_CLEAR_STOP` | ручной стоп | pos_admin, pos_kitchen | dishId, reason | F03 |
| `POS_RECALC_STOP_LIST` | авто-стоп по остаткам и ТТК | pos_admin (и диспетчер) | — | F03 |
| `POS_SAVE_HALL` / `POS_SAVE_TABLE` | справочник залов и столов | pos_admin | … | — |
| `POS_SAVE_MODIFIER_GROUP` / `POS_SAVE_MODIFIER` / `POS_LINK_DISH_MODIFIERS` | модификаторы | pos_admin | … | — |
| `POS_GET_STAFF_REPORT` | выручка, чеки, средний чек по кассирам/официантам за период | pos_admin | dateFrom, dateTo | S08 |

Все мутирующие действия идут через существующий механизм `operationId` (`Idempotency.gs`).
Для `POS_PAY` и `POS_REFUND` клиент **обязан** передавать `operationId` (повтор после обрыва не создаёт вторую оплату).

### Фоновая задача
`posFulfillPendingSales_` — в 15-минутном диспетчере: берёт `SALES` с `источник='касса'` и
`исполнение_статус` пустым/`ошибка_исполнения` (с ограничением повторов), вызывает `fulfillSaleByTtk_`.
Ошибки (нет утверждённой ТТК, не хватает остатка) → задача в `TASKS` шеф-повару + событие в `EVENTS`.
Там же — `POS_RECALC_STOP_LIST` для каждой точки с открытой сменой.

## 4. Что «кусается»

- **Оплата не должна зависеть от склада.** Списание по ТТК может упасть (нет ТТК, минус на остатке).
  Поэтому `POS_PAY` только фиксирует оплату и создаёт `SALES`; списание — асинхронно (п. 3). Кнопка «Списать сейчас» для менеджера.
- **Сессия в фоновой задаче.** `fulfillSaleByTtk_` ждёт `session.location_id`/`organization_id`. Нужна служебная
  сессия по точке (проверить, как это сделано у других задач диспетчера, и сделать так же — не обходить RBAC).
- **Скорость Apps Script.** Вызов 0,5–2 с, лист `SALES` растёт. Меню и зал кэшируем (`CacheService`, 60 с,
  сброс при изменении). Чтения заказов — только по открытой смене. Цель: добавить позицию < 1,5 с.
- **Гонки.** Все мутации под `withLock_`; `version` у заказа — устаревшее изменение отклоняется с понятной ошибкой
  «Заказ изменён на другом устройстве, обновите».
- **«Реалтайм».** Вебсокетов в GAS нет: экраны зала и кухни опрашивают сервер раз в 10 с, только при открытой вкладке.
- **Офлайн.** В первой очереди — нет (только идемпотентный повтор). Касса без интернета не работает — сказать заранее.
- **Часовой пояс.** Смена может пересечь полночь: дата продажи = дата открытия смены (Москва), как в остальных отчётах.
- **Модификаторы со списанием.** Расход продукта модификатора идёт отдельной складской операцией с тем же `cascade_id`.
- **Возвраты.** Возврат не «вскрывает» уже списанное сырьё — возврат денег ≠ возврат продукта на склад
  (решение менеджера: списать как отход или вернуть — отдельная кнопка).
- **Мультиточечность.** Каждая точка — свои залы, смены и стоп-лист; меню — общее для организации.
- **Фискализация (не в этой очереди).** Схема оставляет место: `POS_PAYMENTS.operation_id` станет ключом чека в облачной кассе.

## 5. Порядок сборки

1. **Вертикальный срез (M1).** Листы `POS_SHIFTS`, `POS_ORDERS`, `POS_ORDER_LINES`, `POS_PAYMENTS`;
   действия `POS_OPEN_SHIFT`, `POS_GET_MENU`, `POS_CREATE_ORDER`, `POS_ADD_LINE`, `POS_PAY`, `POS_CLOSE_SHIFT`;
   экран S01 (касса «с собой») + S05 (смена). Продажа → `SALES` → списание по ТТК фоновой задачей.
   Проверка: продать блюдо, увидеть остаток и P&L в «Экономике».
2. **Зал и официант (M2).** `POS_HALLS`, `POS_TABLES`; `POS_GET_FLOOR`, `POS_SEND_TO_KITCHEN`, `POS_PRECHECK`, `POS_MOVE_ORDER`;
   экраны S02 (официант, мобильный), S03 (зал), очередь кухни.
3. **Модификаторы (M3).** Три листа модификаторов, редактор в карточке блюда, выбор в S01/S02, списание продукта модификатора.
4. **Стоп-лист (M4).** `STOP_LIST`, ручной и авто по остаткам; S04; скрытие в меню кассы/официанта.
5. **Отмены, возвраты, отчёт по сотрудникам (M5).** `POS_CANCEL_ORDER`, `POS_REFUND`, `POS_GET_STAFF_REPORT` (S08).
6. **Позже:** CRM/лояльность, QR-меню, чаевые, сайт доставки, фискализация (облачная касса).

## M6 — CRM и бонусы
Листы (новые колонки к существующим — только в конец схемы):
- `GUESTS`: guest_id, organization_id, телефон (+7XXXXXXXXXX, уникален в организации), имя, день_рождения,
  согласие_пд (дата), бонусы (текущий баланс), всего_оплачено, визитов, последний_визит, статус, создано, комментарий.
- `BONUS_TXNS`: txn_id, organization_id, guest_id, order_id, тип (начисление | списание | отмена_начисления |
  возврат_списания | корректировка), сумма (±), остаток_после, создано, user_id, причина. Баланс = сумма проводок;
  поле `бонусы` в GUESTS — кэш, обновляется в той же блокировке.
- `POS_ORDERS` + guest_id, бонусы_списано, бонусы_начислено.
- Настройки в `SETTINGS` (ключи `loyalty.*`): включено, кешбэк_процент (по умолчанию 5), макс_списание_процент (30).

Списание бонусов — это скидка на заказ (поле `скидка`), а не способ оплаты: скидка распределяется по строкам,
и в продажи (SALES) и в будущий чек 54-ФЗ идут цены со скидкой. Начисление — от суммы, оплаченной деньгами.
Возврат: возвращаются деньги за позиции с учётом скидки, гостю — пропорциональная часть списанных бонусов,
начисленные за эти позиции бонусы отменяются (баланс не уходит ниже нуля — разница пишется в причину).

Персональные данные (152-ФЗ): гость создаётся только с отметкой согласия; кассир/официант видят имя и последние
4 цифры телефона, полный телефон — менеджер и директор. Удаление по запросу гостя — обезличивание карточки.
