## 1. Что сделано

| Функция ТЗ | Как сделано |
|---|---|
| Залы и столы | Залы площадки (SiteID из `Площадки_V97`), столы с номером, местами мин/макс, местом на сетке, формой, связями «можно объединять» (пишутся у обоих столов). Ничего не удаляется — «в архиве». В архив не уходят зал или стол с предстоящими бронями |
| Схема зала | Сетка зала, столы с состоянием на выбранные дату и время: свободен / бронь в ближайшие 2 ч / забронирован / гости за столом. Карточка стола: брони дня, «Забронировать этот стол» |
| Бронирование | Карточка по ТЗ §4.2: гость, телефон, дата, начало, продолжительность, окончание (считается), гостей, зал, столы, пожелания, комментарий, менеджер, предзаказ, статус |
| Статусы | НОВОЕ → ПОДТВЕРЖДЕНО → ГОСТЬ ПРИШЁЛ → СТОЛ ЗАНЯТ → ЗАКРЫТО; ОЖИДАНИЕ, ОТМЕНЕНО, NO-SHOW. Недопустимые переходы отклоняются. Отмена и «не пришёл» — только с причиной; «не пришёл» — только после начала брони; отмена отменяет предзаказ |
| Контроль столов | На сервере, под общей блокировкой: пересечение интервалов по каждому столу, вместимость, действующие зал и стол, несколько столов — только связанные объединением, один зал. Стык интервалов (21:00–21:00) разрешён. Лист ожидания столы не держит; при подтверждении проходит все проверки |
| Календарь | День, неделя, месяц; список предстоящих; раздел «Зал» главного окна: брони сегодня, «скоро», лист ожидания, неделя |
| Предзаказ | Блюда и напитки из каталога `Блюда` (без второго справочника), количество, единица (порц, шт, г, мл), вес/объём, курс, гость, комментарий. Черновик → подтверждён. **Не продажа**: склад, журнал продаж и списания не меняются (проверено тестом) |
| Прогноз потребности | По подтверждённым предзаказам: блюда по дням, отдельно кухня и бар (бар — цех «Бар» в листе `Блюда`). Склад не резервируется |
| Конвертация предзаказа в заказ | Поле `ConvertedOrderID` и статус CONVERTED готовы; кнопка «Открыть заказ по бронированию» — этап 3 (блокнот официанта) |

## 2. Надёжность (ТЗ §15)

* **Ключ операции (IdempotencyKey).** Каждое записывающее действие страницы несёт ключ; ключ живёт до ответа сервера. Повтор после обрыва связи идёт с тем же ключом — сервер возвращает прежний ответ, вторая запись не создаётся (лист `Идемпотентность_V1`, не кэш). Тот же ключ другим действием — отказ. Без ключа запись не принимается.
* **Журнал транзакций.** План записи (полные строки) сохраняется до записи (`ЖурналТранзакций_RS`: PENDING → COMMITTED). Незавершённую транзакцию `rsTxRecover` доводит по плану; повтор не дублирует строку и не затирает более новую версию.
* **Оптимистичная блокировка.** Изменение передаёт версию, которую видел сотрудник; другая версия — «запись уже изменил другой сотрудник».
* **История.** Каждое изменение — строка `СобытияОбслуживания_V1` (было → стало) и запись в `Audit_Log` с цепочкой хешей. В истории телефон скрыт.
* **Пакетное чтение**: каждый лист читается одним запросом.

## 3. Безопасность

* Шлюз: все новые функции зарегистрированы с правами (`MC_GATE_EXT_`), записывающие — с защитой шлюза от двойного нажатия. Проверка `tools/gatecheck.js`: незарегистрированных вызовов со страниц нет (одно срабатывание `norm` — ложное, было до этапа).
* Права: `hall_view` — схема и брони; `booking` — брони и предзаказ; `hall_manage` — настройка зала и досдача операций.
* Роли: «Директор» — всё; «Администратор» (существующий администратор зала) — всё; новая роль «Официант» — схема зала и каталог; бронирование официанту, «Администратору площадки» и «Руководителю смены» директор выдаёт индивидуальным правом. Повар зал не видит.
* Телефон гостя — персональные данные: полностью виден только с правом `booking`, остальным — последние 2 цифры.

## 6. API

| Функция | Право | Что делает |
|---|---|---|
| `rsHallData({siteId,date,time})` | hall_view / booking / hall_manage | залы, столы с состоянием, брони дня |
| `rsHallSave`, `rsTableSave` | hall_manage | зал, стол (с ключом и версией) |
| `rsBookingList({siteId,from,to})` | hall_view / booking | брони за период (≤ 62 дня) с предзаказами |
| `rsBookingAvailability({siteId,date,start,duration,excludeId})` | hall_view / booking | столы: свободен или чем занят |
| `rsBookingCreate`, `rsBookingUpdate`, `rsBookingStatus` | booking | бронь, изменение, статус |
| `rsPreorderSave({bookingId,version,items,confirm})` | booking | предзаказ: черновик / подтвердить |
| `rsPreorderForecast({siteId,from,to})` | hall_view / booking / plan | потребность по подтверждённым предзаказам |
| `rsBookingHistory({id})` | booking | события брони |
| `rsDishCatalog()` | booking / hall_view / catalog | действующие блюда: код, название, категория, цех, выход (без себестоимости и состава) |
| `rsTxRecover({force})` | system / hall_manage | досдать незавершённые транзакции |

Ответ — единый формат MON CHEF `{success, operation_id, data | error{code,message}}`; новый код ошибки `CONFLICT` — пересечение брони или чужое изменение.

## 8. Ограничения

* Стенд — имитация Apps Script: блокировка, квоты и время выполнения настоящего Google не проверены. Перед пилотом — проверка на копии рабочей таблицы (аудит, §13).
* Схема зала обновляется раз в минуту и после каждого действия; мгновенного обновления между устройствами нет.
* Объединение столов задаёт администратор; система не подбирает столы сама.
* Без площадок V97 работает одна «Основная площадка» (SITE-MAIN).
* «Занят заказом» на схеме появится с блокнотом официанта (этап 3).
