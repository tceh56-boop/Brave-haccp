## 1. Фактическая архитектура

* 145 серверных файлов, 52 201 строка, 3 373 функции верхнего уровня, из них 1 121 публичная (без `_` в конце).

### 1.4. Слои приложения

```
Браузер: Console.html (SECTIONS — 21 раздел меню, VIEWS — 72 экрана) + 22 отдельные страницы
   │  google.script.run (+ служебный аргумент {__mct} — ключ входа, MonChef_Pages.gs)
   ▼
zzz_MonChef_Gate.gs  — оборачивает ВСЕ публичные функции (идёт последним в проекте)
   сессия → право (MC_GATE_NEED_) → медицинский допуск (_mcComplianceGate_) → защита от двойного нажатия (15 с)
   → OperationID → блокировка → функция → аудит → ответ
   ▼
Модули: Code.gs (ядро) + MonChef_*.gs + MonChef_V4…V100_*.gs
   ▼
Google Sheets (одна таблица на предприятие: MC_SHEET_ID / MC_INSTALL_SHEET_ID_ / запасная константа)
Google Drive (фото блюд, ТТК, накладные, бэкапы, архив журналов)
CacheService (сессии, защита от повтора, кэш чтения) · PropertiesService (соль ПИН, счётчик операций, настройки)
```

Модули расширяют друг друга **подменой функций при загрузке**: 22 файла присваивают новое тело уже объявленной функции (`mcSaleAdd`, `addSaleEntry`, `calculateKBZHU`, `getNutritionData`, `doGet`, `_UI_BUILDERS_.*`, `_mcViewOfParams_` и др.). Поэтому результат зависит от **порядка файлов в проекте**. Шлюз должен загружаться последним, это держится на имени `zzz_`.

## 4. Дублирующиеся и конфликтующие механизмы

1. **Три манифеста** с разными сведениями, все неточные (§1.3).
2. **Две ветки кода** с одинаковыми номерами модулей (§1.6).
3. **Две карты разделов меню**: `UI_SECTIONS` объявлен в `MonChef_UI.gs:12` и переобъявлен в `MonChef_UISections.gs:7`; на клиенте — свой `SECTIONS` в `Console.html`. Новый раздел нужно добавлять во все три места и в `MC_RB_SECTIONS_`.
4. **Три справочника продуктов**: `Продукты_Справочник`, `Продукты_ID_V53`, `Продукты_Карточки_V96`. Новых не создаём; блюдо продаётся по коду из `Блюда`, ингредиенты — по ProductID V53.
5. **Продажа = сразу списание** (V71). Для зала по ТЗ производство, подача и оплата — разные события (§12 ТЗ). Если провести заказ через `mcSaleAdd`, склад спишется в момент продажи, а при повторном вызове на производство — второй раз. Решение — §6.3.
6. **Блюдо в продаже определяется по названию** (`mcSaleAdd: d.dish`), а не по коду. Для заказа зала используется код блюда и версия ТТК, название — только для показа.

### 6.3. Склад: когда списывать (ТЗ §11–12)

* **Отправка на кухню** — задание в очереди, **склад не трогается**.
* **Отмена до начала приготовления** — задание отменено, расхода нет.
* **«Готовится» → «Готово»** — фактическое производство: списание по партиям тем же движком V71 (выделяется внутренняя функция «списать по ТТК под позицию», без записи в J36), связь партия → `OrderItemID`, себестоимость по партиям. Повар может подтвердить фактический расход, если он отличается от ТТК.
* **Отмена после начала приготовления** — уже списанное остаётся расходом, причина — потери (V64 «Отходы и брак»), позиция отменена с основанием.
* **Подача гостю** — отдельное событие (время, кто подал), склад не трогается.
* **Оплата** — подтверждение из кассы (сверка по Z-отчёту V94, затем адаптер кассы) → строка J36 **без повторного списания** (с пометкой «склад списан производством, OrderItemID …»). Экономика V64 берёт выручку из J36, себестоимость — из производства.
* Сторно оплаченной позиции — механизм V95 с учётом того, что продукты уже израсходованы (возврат на склад только для неприготовленного товара).

## 7. Транзакции и восстановление (ТЗ §15)

Пример — отправка заказа на производство:

1. Под блокировкой: проверить `IdempotencyKey`. Если ключ уже есть — вернуть сохранённый ответ.
2. Записать в `ЖурналТранзакций_RS` строку `PENDING` с полным планом изменений (какие строки и в какие листы).
3. Выполнить запись **пачкой** по листам; после каждого листа — отметка шага.
4. Отметить `COMMITTED`, сохранить ответ под `IdempotencyKey`, отметить изменение (`_mcGenBump_`), записать аудит.
5. Проверка «незавершённые операции» (кнопка у администратора и проход в существующем `monChefFrequentTick`): `PENDING` старше 6 минут повторяется по сохранённому плану. Каждый шаг идемпотентен (строка с тем же ID повторно не создаётся).

## 8. Публичное меню (ТЗ §5, §14)

* Адрес `?menu=1&site=SITE-…` → страница `GuestMenu.html` без входа.
* Данные — функция `rsPublicMenu(siteId)` в `MC_GATE_PUBLIC_`. Она отдаёт **снимок**, который собирает администратор при публикации (лист `МедиаМеню_V1` + кэш). В снимке только: код, название, категория, цена продажи, вес или объём продажи, описание, состав (названия ингредиентов без количеств — уточнить, §11 вопрос 6), утверждённое КБЖУ или «КБЖУ не определено», аллергены, медиа, доступность (GO/STOP/LIMITED без причины).
* Нет: закупочных цен, себестоимости, ТТК, партий, сотрудников, внутренних ID листов, причин STOP.
* Заказ гостя — режим «предзаказ / вызов официанта»: заявка ждёт подтверждения официанта или администратора. Подтверждение привязывает её к столу или брони. Без подтверждения заявка не попадает на кухню.
