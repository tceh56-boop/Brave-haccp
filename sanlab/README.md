# San.Lab — CRM санитарного сопровождения

Apps Script + Google Sheets + Drive + Calendar + HTML/CSS/JS. Реализация ТЗ v1.0 (этапы 1–6) и инструкции пользователя по ролям.

## Состав

```
dist/gas/          ← готовый проект Apps Script (27 файлов + appsscript.json, .clasp.json)
dist/demo/         ← демо в одном HTML (то же ядро и тот же интерфейс, хранилище в браузере)
src/core/*.gs      ← бизнес-логика (общая для GAS и демо)
src/gas/*.gs       ← платформа Google: SheetsStore, GoogleIntegrations, Setup, Code
src/ui/*.html      ← интерфейс (Index, Styles, App, PagesHome/Visits/Work/Biz)
tests/             ← приёмочные проверки AT-01…AT-15 (ядро и GAS-адаптеры на имитации Google)
tools/build.py     ← сборка dist/
```

Модули по разделу 13.1 ТЗ: `Code.gs` (вход), `AuthService.gs` (роли, права, аудит), `VisitService.gs` (+ Calendar), `ChecklistService.gs`, `FileService.gs`, `ReportService.gs`, `LabService.gs`, `TaskService.gs`, `FinanceService.gs`, `DashboardService.gs` (+ уведомления, фоновые задачи), `Validation.gs`, `Repository.gs`, `ClientService.gs`, `Api.gs` (маршрутизация).

## Развёртывание (≈15 минут)

1. **script.google.com → Новый проект** под аккаунтом владельца (руководитель, Google Workspace).
2. Перенесите все файлы из `dist/gas/` (имена без изменений; `.html` — как HTML-файлы). Либо `clasp push` с `.clasp.json` (вставьте `scriptId`).
3. Настройки проекта → «Показывать файл appsscript.json» → замените содержимым из `dist/gas/appsscript.json`.
4. Выберите функцию **`setup`** → Выполнить → выдайте разрешения. Создаются:
   - таблица `SANITARY_ERP_DB` (19 листов, защищены от прямой правки), 
   - папка `San.Lab` со структурой `00_ADMIN … 06_EXPORTS_BACKUPS`,
   - настройки по умолчанию, вы — как Руководитель,
   - 3 чек-листа и 5 услуг (критерии — проект, утвердите в «Настройках»),
   - триггеры: ежедневная проверка (7:00), уведомления (каждые 15 мин), резервная копия (2:00).
5. **Развернуть → Новое развёртывание → Веб-приложение**: «Выполнять от имени: я», «Доступ: пользователи домена». Ссылку раздайте сотрудникам.
6. В приложении: «Сотрудники» → добавьте людей с их рабочими e-mail и ролями; заполните своё ФИО.

**Если нет Google Workspace** (обычные gmail.com): `getActiveUser()` не вернёт e-mail сотрудника. Переключите `AUTH_MODE` = `PIN` в «Настройках → Параметры», задайте сотрудникам PIN (форма сотрудника или `setPin(email, pin)`), доступ веб-приложения — «Все, у кого есть аккаунт Google». 5 неверных попыток → блокировка на 15 минут.

**Тестовая копия:** в отдельном проекте после `setup()` запустите `seedDemoData()` — демо-данные без писем и событий календаря. В рабочей базе не запускать.

## Что сделано по ТЗ

| Требование | Где |
|---|---|
| Постоянные ID `VIS-000842` и т.д., не зависят от строки, не переиспользуются | `Repository.newId`, счётчики в Script Properties |
| Сервер проверяет права на действие и на запись; скрытая кнопка — не защита | `PERMS` + `Auth.visit/visitWrite/canSee` |
| Идемпотентность: повтор запроса не создаёт дублей записей, файлов, событий | `request_id` в `Api.handle`; Calendar ищет событие по тегу `[VIS-…]` |
| Запись атомарна: при ошибке в таблицу не попадает ничего | пакетная запись `SheetsStore` (commit/rollback) |
| Серверное время, AuditLog, row_version | `Repo.create/update`, `Audit.log` |
| Чек-лист версионируется; выезд привязан к версии | `Checklists.saveVersion` |
| Обязательные фото, документированное исключение | `Checklists.missing`, `Results.waivePhoto` |
| Фото не удаляются — помечаются неактуальными с причиной | `Files.invalidate` |
| Отчёт: снимок, версии, возврат с обязательным комментарием + задача, PDF при утверждении | `ReportService` |
| Независимая проверка (свой отчёт / своя задача) | `INDEPENDENT_REVIEW` |
| Проба: 7 статусов, обязательные поля для перехода, сроки по типу, просрочки | `LabService` |
| Задачи: источник, приоритет, срок, проверка, напоминания, эскалация | `TaskService` |
| Финансы: начисление ≠ счёт ≠ оплата; частичные оплаты; корректировки на утверждение; баланс по операциям | `FinanceService` |
| Резервные копии с ротацией, восстановление | `backupNow`, `restoreFromBackup(id)` |

## Нормативная база, ППК и ТУ

`DocsService.gs`, `NormSeed.gs`, интерфейс — `PagesDocs.html`. Разделы меню: «Программы ПК», «Технические условия», «Нормативная база».

- **Нормативная база** (листы `NormDocs`, `NormItems`): документы со сроками действия и положения, разложенные по видам — лабораторный контроль, ККТ, журналы, медосмотры, аварийные ситуации, мероприятия (для ППК); микробиологические показатели по группам продукции, маркировка, методы контроля, тексты разделов (для ТУ). У каждого положения есть отметка «сверено с официальным текстом». Любая правка снимает отметку; сверку подтверждают руководитель или контролёр с указанием источника. За `NORM_EXPIRY_WARN_DAYS` дней до окончания действия документа руководитель получает уведомление.
- **ППК** (лист `Programs`): по объекту и его признакам (горячий/холодный цех, дети, собственная вода и т. д.) собираются разделы по перечням СП 1.1.1058-01: нормативные документы, ответственные, лабораторный контроль, медосмотры, ККТ, аварийные ситуации, формы учёта, мероприятия. Черновик редактируется, утверждается в PDF (папка `01_CLIENTS/<клиент>/PPC` и «Документы»), версии сохраняются, срок пересмотра — `PPC_REVIEW_MONTHS` или раньше, если заканчивается действие использованного норматива.
- **ТУ** (лист `TechSpecs`): разделы по ГОСТ 2.114-2016 (п. 5.1.1, 5.3.1), показатели — из базы по группе продукции, обозначение `ТУ ОКПД2-номер-ОКПО-год` (ОКПО по умолчанию — `ORG_OKPO`). Изменения ТУ — новая версия с тем же обозначением.
- **Загрузка ТТК** (`TtkImport.html`): в форме ТУ кнопка «Загрузить ТТК (.docx)». Файл читается в браузере, по разделам ТТК (ГОСТ 31987-2012) заполняются наименование, область применения, рецептура (масса нетто, выход), органолептика, физико-химия, пищевая ценность, срок годности, условия хранения, упаковка; группа продукции подбирается по наименованию. Пользователь проверяет поля перед сборкой. Исходный файл ТТК сохраняется в `01_CLIENTS/<клиент>/TU` и в «Документах» (тип `TTK`), в ТУ появляется ссылка на ТТК № и раздел «Пищевая и энергетическая ценность». Микробиология из ТТК не переносится — подставляются нормативы из базы.
- Документ с несверенными положениями утверждается только руководителем с обоснованием; в PDF такие строки выделены, обоснование напечатано на титуле.
- Стартовое наполнение, сверенное по текстам заказчика (с номерами пунктов): ТР ТС 034/2013 (микробиология, маркировка), Положение о знаке ЕАС, ГОСТ 2.114-2016, СанПиН 2.3/2.4.4282-26 (журналы прил. 1–5, осмотр персонала, приёмка, уборка, мойка посуды, фритюр, суточная проба), СП 2.1.4284-26 (вентиляция, отходы, уборочный инвентарь, дезинсекция), СП 2.2.4285-26 (ПК условий труда, микроклимат не реже 1 раза в год), ТР ТС 022/2011 (ст. 4: состав маркировки, аллергены, даты, пищевая ценность), ТР ТС 005/2011 (ст. 5–6), ГОСТ Р 1.3-2018 (разделы и обозначение ТУ), ГОСТ 30390-2013 (безопасность, приёмка, хранение, информация потребителю), МУК 4.2.1847-04 (обоснование срока годности).
- Периодичность лабораторного контроля нормативы 2026 года не устанавливают — её определяет предприятие (п. 4 СанПиН 2.3/2.4.4282-26, п. 10, 13, 15 СП 2.2.4285-26). Типовые значения, мероприятия и действия при авариях вынесены в отдельный документ «Типовые решения ППК» (предложения San.Lab, утверждаются руководителем предприятия в составе ППК).
- Требуют сверки (текстов нет): ТР ТС 021/2011, 52-ФЗ, 29-ФЗ, приказ Минздрава № 29н, МР 2.3.6.0233-21, СП 1.1.1058-01, СанПиН 1.2.3685-21, СанПиН 3.3686-21, стандарты методов испытаний.

- **Реестр журналов J01–J53** (`JournalCatalog.gs`, по реестру заказчика): у каждого журнала — назначение, основание (пункт СанПиН 2.3/2.4.4282-26 и др.), периодичность, ответственный, тип заполнения, пересечения, колонки бланка. По признакам объекта система выбирает журналы, которые нужно вести, и не включает дубли (например, J01 и J25 ведутся в форме J42, J07/J08/J27 — в журнале здоровья J44). В ППК раздел «Реестр журналов» с номерами J; в комплекте — документ «Реестр журналов» со статусом каждого из 53 журналов («ведётся — документ № …», «дублирует …», «не применяется: нет признака …») и бланки журналов по формам заказчика: шапка, «Начат / Окончен», 15 строк, для J42/J44/J46 — сетка по дням месяца, для J41 — методика оценки фритюрного жира, J45 — медосмотры и прививки, J51 — бактерицидная установка.
- **Чек-листы ППК**: при сборке программы формируется раздел «Чек-листы» — J11 открытие смены, J12 закрытие смены, приёмка сырья (CL-ПР), еженедельный санитарный (CL-НЕД), санитарный день J49, самоконтроль по ППК (CL-ПК, собирается из реестра журналов, лабораторного контроля и медосмотров программы), внутренний аудит ХАССП. Пункты привязаны к положениям нормативной базы (основание и отметка сверки) и признакам объекта (фритюр, дети, бактерицидные лампы, sous-vide). Пункты можно править и добавлять, в том числе свой чек-лист со своим кодом; в комплекте каждый чек-лист — отдельный бланк с колонками «Основание», «✓/✗/НП», «Комментарий / действие».
- Содержание ППК и ТУ хранится частями в колонках `content_json`…`content_json4` (до 180 000 символов). После обновления обязательно запустите `setup()` — он добавит колонки; без них крупная программа не сохранится (система сообщит об этом, данные не теряются).
- **Комплект ППК + ХАССП (ZIP)** — `PackService.gs`, кнопка «Комплект документов (ZIP)» в карточке программы. По образцу комплекта заказчика собирает в один архив документы Word: паспорт комплекта, ППК, план ХАССП, приказы, схему потоков, реестр документов (с ТУ клиента из системы), ТТК-шаблоны и карты ККТ, лабораторную программу, инструкции, журналы (включая журналы из нормативной базы), чек-листы, график работы, памятку по маркировке, лист ознакомления, реестры поставщиков и оборудования, график санмероприятий, справку по нормативной базе. Документы про sous-vide, жарку/томление, вакуумирование, термообработку включаются только при соответствующих признаках объекта; нумерация сплошная. DOCX и ZIP собираются на чистом JS (`DocxWriter.gs`), архив сохраняется в `01_CLIENTS/<клиент>/PPC` и в «Документах» (тип `PPC_PACK`).
- СанПиН 2.3/2.4.4282-26, СП 2.1.4284-26, СП 2.2.4285-26 действуют с 01.09.2026 до 01.09.2032; СанПиН 2.3/2.4.3590-20 и СП 2.2.3670-20 утратили силу 01.09.2026 (по текстам постановлений 2026 года).

После обновления установленной системы запустите `setup()`: он создаст новые листы, добавит недостающие документы и обновит документы, которые вы ещё не сверяли сами, до текущего наполнения (старые несверенные положения выключаются, сверенные вами — не трогаются; повторный запуск ничего не дублирует).

## Приёмочные проверки

`node tests/run_tests.js` — ядро в памяти; `PLATFORM=gas node tests/run_tests.js` — тот же набор через `SheetsStore`/`GoogleIntegrations`/`Setup` на имитации сервисов Google (проверяет и то, что даты пишутся в ячейки датами). Оба прогона: **22/22** (AT-01…AT-21 + права ролей; AT-16…AT-21 — нормативная база и её обновление в установленной системе, ППК, ТУ, сроки нормативов, комплект ППК в ZIP с реестром журналов и чек-листами, ТУ на основе ТТК). Результат последнего прогона — `tests/results.json`.

На реальном аккаунте перед пилотом обязательно пройдите вручную: AT-02 (событие появилось в Calendar), AT-08 (PDF открывается, фото видны), AT-13 (временно укажите несуществующий `CALENDAR_ID`), AT-14 (`backupNow()` → `restoreFromBackup(ID копии)`), AT-12 (вход отключённого сотрудника).

## Ограничения и решения для согласования

- **Квоты Apps Script.** Каждый запрос читает нужные листы целиком. Для 10+ сотрудников и тысяч выездов в год это нормально; при ~50 тыс. строк в одном листе понадобится архивирование `AuditLog`/`Notifications` или переход на БД (раздел 18 ТЗ).
- **Офлайн-режим** не реализован: есть черновики комментариев на устройстве и предупреждение о несохранённом. Фото без сети не загрузятся.
- **PDF** собирается из HTML средствами Apps Script (без шаблона Google Docs). Если нужен фирменный бланк в Docs — это отдельная доработка `ReportHtml.render`.
- **Критерии чек-листов** в базовой поставке — проект со ссылками на СанПиН 2.3/2.4.3590-20, ТР ТС 021/2011. Утвердите их и укажите ответственного (поле «Основание критериев»).
- **Персональные данные** (152-ФЗ): до запуска проверьте юридически допустимость хранения в Google Workspace, сроки хранения фото и отчётов (раздел 14.2 ТЗ). GPS не используется.
- **Идемпотентность** хранится в кэше скрипта 6 часов — повтор того же запроса позже создаст новую операцию только для действий без естественной защиты (создание задачи/клиента; дубли клиентов и начислений отсекаются отдельно).
