# Stage 110 — Журналы контроля из ККТ (шаг 4 плана) и чистка системы

## Цепочка

```
ТТК блюда / техкарта ПФ
  → предложение ККТ (TTK_CCP_PROPOSALS)
  → решение технолога: числовой предел + пункт документа
  → контроль и предел в ЧЕРНОВИКЕ ППК (сразу подтверждённые, с продуктом)
  → утверждение ППК (шлюз готовности)
  → журналы контроля (JOURNAL_DEFINITIONS) с нормой из предела и расписанием
  → выпуск партии → ожидающая запись → измерение
  → в норме: запись; вне нормы: отклонение + корректирующее действие
```

## Что изменено

1. **Перенос ККТ в ППК** (`_tnMaterializeCcp_`). Решение технолога в ТТК с числовым
   пределом и пунктом документа считается подтверждением человеком. Поэтому контроль
   попадает в черновик ППК со статусом `CONFIRMED` и `human_confirmed = true`, а предел — со
   статусом `CONFIRMED`. Иначе шлюз готовности `buildPpkReadinessGate_` не дал бы утвердить
   ППК. В `product_id` записывается блюдо или ПФ, и движок ХАССП применяет контроль только
   к этому продукту.
2. **Новая версия ППК.** Контроли из предыдущей версии в новую не копируются. Поэтому
   `TRANSFER_TTK_CCP_TO_PPK` переносит в черновик все принятые точки, которых там ещё нет,
   включая уже перенесённые в прошлые версии. Точки архивных ТТК и техкарт не переносятся.
3. **Журналы при утверждении ППК** (`generateCcpJournals_`). Вызываются из
   `approvePpkVersion_`; если вызов не удался, утверждение не отменяется, а журналы можно
   доформировать действием `GENERATE_CCP_JOURNALS`. Правила:
   * журнал создаётся по одному на каждый подтверждённый контроль из ТТК или техкарты ПФ;
   * для приёмки сырья журнал не создаётся: это общий журнал приёмки, а не журнал блюда;
   * норма берётся из предела, текст вопроса — «параметр, норма — блюдо»;
   * в журнал записываются вид и идентификатор продукта (`parent_type`, `parent_id`) и
     ссылка на предложение;
   * журналы ККТ прежних версий ППК уходят в архив;
   * повторный вызов журналы не дублирует.
4. **Периодичность** берётся из частоты ККТ:

   | Частота ККТ | Журнал |
   |---|---|
   | каждая партия | `по_партии`: запись при выпуске партии, не по слотам смены |
   | каждые N ч | триггер `КАЖДЫЕ_N_МИНУТ` |
   | 2 раза в смену | триггеры в начале и в конце смены |
   | PRP (аллергены) | вопрос ДА/НЕТ раз в смену |
   | прочее | раз в смену |

5. **Партии** (`createCcpBatchPending_`, вызывается из `_completeProduction_`). Для каждого
   действующего журнала ККТ «по партии» этого блюда или ПФ создаётся ожидающая запись
   «Партия K-0001: температура в толще изделия, норма: не ниже 75 °C — Французская котлета».
   Повторно по той же партии запись не создаётся. Значение вводит сотрудник, а оценку
   делает существующий `_evaluateJournalValue_`: вне нормы — отклонение и корректирующее
   действие с задачей.
6. **Слоты смены.** `generateJournalSlotsForLocation_` не создаёт записи по расписанию
   смены для журналов «по партии».
7. **Интерфейс.** На вкладке HACCP в ТТК и в техкарте ПФ появился блок «Журналы контроля»:
   норма, когда заполнять, последняя запись и число открытых отклонений.

## Исправлено в движке ХАССП

`runHaccpDecisionEngine_`: если значение не передано, выражение `Number('')` давало 0, и
любой предел с нижней границей давал BLOCK. Например, приёмку сыра при отсутствии
измерения заблокировал бы предел «не ниже 75 °C». Теперь нет измерения — нет оценки.

## Чистка системы (отдельный коммит)

* **`gas/Index.html`.** Удалён хвост из ~2870 строк после `</html>` — устаревшая обрезанная
  копия страницы. Всё её содержимое есть выше. Браузер показывал её текстом внизу
  приложения, и из-за неё на каждой загрузке была ошибка «Unexpected token '<'». После
  удаления страница загружается без ошибок.
* **`Config.ROLE_ACTION_DENY`.** Роли ПОВАР и КЛАДОВЩИК были объявлены дважды, и
  действовало только второе вхождение. Списки объединены. Для КЛАДОВЩИКА это вернуло
  запреты `RELEASE_QUARANTINE`, `RELEASE_SEMI_FINISHED_QUALITY` и `RESOLVE_CRITICAL_INCIDENT`:
  они были в перекрытом вхождении, как и у ПОВАРА, а на деле кладовщику были разрешены.
* **`CascadeEngine`.** Удалён повтор ключа `начато`.
* **`Production`.** Повторное `var ttk` переименовано в `currentTtk` (поведение то же).
* **`DEPLOY_MANIFEST.json`** пересобирается скриптом `tools/build_manifest.py`. Раньше в нём
  были неверные хеши и не хватало файлов.
* **ESLint** (no-dupe-keys, no-redeclare, no-unreachable, no-duplicate-case, no-dupe-else-if,
  no-self-assign, no-func-assign, no-dupe-args) не находит замечаний во всех `.gs` и
  скриптах `Index.html`.

**Не удалялось.** 69 функций нигде не вызываются по имени. Почти все — тесты этапов и
миграции, их запускают вручную из редактора Apps Script. Остальные могут вызываться
триггерами или заготовлены под API, поэтому удалять их вслепую не стоит:
`confirmInvoiceReceipt_`, `syncOfflineQueue_`, `getRecursiveBatchCostTrace_`,
`deactivateProductAllergen_`, `archiveWorkshop_`, `createWriteoffReason_`,
`createHaccpDeviation_`, `getAuditLog_`, `findProductFast_`, `calculateCanonicalCost_` и др.
Решение по ним — за владельцем кода.

## Проверено

Сквозной прогон в Node на настоящих модулях Ppk, PpkGenerator, TechSpec, TechNorms,
TtkImport, PfTech, TTK, Recipes, SemiFinished, Products, FoodCost, CcpJournals, Journals и
OperationalClosureStage11; таблицы в памяти:

* импорт котлеты с двумя ПФ; приняты ККТ нагрева (≥ 75), раздачи (≥ 65), приёмки и
  охлаждения ризотто (≤ 6);
* в черновике ППК 4 контроля `CONFIRMED`, с продуктом; шлюз готовности — `READY`;
  настоящий `approvePpkVersion_` утверждает ППК;
* созданы 3 журнала: котлета «по партии», раздача каждые 2 ч, ризотто «по партии»;
  приёмка пропущена; повторная генерация журналы не дублирует;
* партия K-0001 → ожидающая запись; повторно по той же партии — нет; слоты смены не
  создают записи для журналов «по партии»;
* 70 °C → критическое отклонение и корректирующее действие; 80 °C → норма;
* приёмка сырья без измерения и при 4 °C → PASS (до исправления — BLOCK);
* новая версия ППК: перенесены 4 точки, повторный перенос пуст; после утверждения
  3 активных журнала новой версии, 3 журнала прежней — в архиве.

Блок журналов проверен в Chromium.

Запустите `runAllMigrations()`: он добавит в `JOURNAL_DEFINITIONS` колонки `parent_type`,
`parent_id` и `ccp_proposal_id`.
