# Stage 111 — Приёмка сырья по документу: распознавание из МонШеф

Из МонШеф перенесён распознающий контур (версии V10–V12 и PdfOcr). В ЦЕХ он встроен в существующую
цепочку приёмки: черновик → проверка целостности → ХАССП → подтверждение человеком → партии. В МонШеф
этот контур проработан глубже, чем был в ЦЕХ. Прежний разбор (`parseSupplierInvoiceText_`) читал
только «плоский» текст OCR регулярными выражениями: строки таблицы часто склеивались, номенклатура
сопоставлялась только по точному названию.

## Цепочка

```
фото / PDF документа
  → Yandex Vision (модель page; при слабом результате второй проход handwritten)
  → восстановление таблицы по координатам слов (с поправкой на наклон снимка)
  → YandexGPT: реквизиты, строки, количество, цена, сумма (без выдумывания: нечитаемое — пусто)
  → сверка арифметики, калибровка уверенности; при сомнениях — второй проход модели (аудит)
  → сопоставление строк с номенклатурой и поставщика со справочником
  → черновик приёмки: целостность документа, ХАССП по каждой строке, подсказка срока годности
  → правка человеком (продукт, количество, цена, даты, этикетка, исключение строки)
  → проводка: партии на склад; выбранные вручную соответствия запоминаются
```

## Что перенесено и как адаптировано

| МонШеф | ЦЕХ (`gas/InvoiceRecognitionCore.gs`) |
|---|---|
| PdfOcr: асинхронное распознавание многостраничного PDF, склейка страниц | `_irOcrAsync_`, `_irMergePages_` |
| `_rebuildTableText_` с оценкой наклона | `_irRebuildTableText_`, `_irSkew_` |
| V10: два прохода OCR, оценка качества, извлечение моделью, сверка арифметики | `_irBestVision_`, `_irQuality_`, `IR_EXTRACT_PROMPT`, `_irFinalize_` |
| V11: латиница → кириллица, нечёткое сравнение (Левенштейн), алиасы | `_irNorm_`, `_irFuzzy_`, `irMatchProduct_`, лист `OCR_ALIASES` |
| V12: калибровка уверенности, второй проход-аудит, ключ поставщика | `_irCalibrate_`, `IR_AUDIT_PROMPT`, `_irApplyAudit_`, `_irSupplierKey_` |
| Классификация документа | УПД, счёт-фактура, товарная накладная, платёжное поручение, кассовый и товарный чек |

Модель недоступна или не настроена: строки разбираются шаблоном по восстановленной таблице, а в
документе появляется предупреждение «проверьте каждую строку».

## Сопоставление с номенклатурой

Порядок: штрихкод → артикул → запомненное соответствие (сначала этого поставщика) → точное
название или внутреннее название → нечёткое сравнение (до 5 кандидатов).

* Нечёткое совпадение подставляется само, только если похожесть ≥ 92 % и отрыв от второго
  кандидата ≥ 8 пунктов. Иначе строка получает список похожих, и продукт выбирает человек.
* Соответствие запоминается (`OCR_ALIASES`), только когда продукт выбрал или подтвердил человек:
  при ручном выборе и при проводке строк с нечётким совпадением. Догадка системы не запоминается.
* Соответствия и номенклатура видны только своей организации.
* Единица в документе отличается от единицы продукта (например, «шт» и «л») — предупреждение:
  количество может быть указано не в тех единицах.

## Срок годности и этикетка

* **Подсказка срока.** Если в документе срока нет, система берёт его из справочника сроков
  (`PRODUCT_SHELF_LIFE`) по глобальному продукту. Режим выбирается в порядке: холодильник,
  комнатная температура, морозильник. Подсказка показывается кнопкой с источником и отметкой
  «не проверено технологом». Сама в строку она не записывается — её применяет человек.
* **Этикетка.** Скан этикетки в строке («📷 Этикетка») записывает дату изготовления, срок
  годности и штрихкод. Если штрихкод этикетки не совпадает со штрихкодом продукта, выводится
  предупреждение.

## Черновик и проводка

* Ошибки проверяются по каждой строке: нет продукта, количество ≤ 0, цена не число, блокировка
  ХАССП. Одна плохая строка больше не блокирует весь документ. Статусы:
  * `READY` — все строки в порядке;
  * `PARTIAL` — есть строки с ошибками;
  * `BLOCKED` — проверка целостности дала CONFLICT, DUPLICATE или REVIEW, либо нет ни одной
    принимаемой строки.
* Документ в статусе `PARTIAL` проводится только с явным согласием на частичную приёмку
  (`allowPartial`). Сервер это проверяет, а интерфейс спрашивает подтверждение.
* Тот же документ, загруженный повторно, блокируется проверкой целостности.
* Правка черновика (`UPDATE_INVOICE_DRAFT`) пересчитывает его целиком. Проведённый документ не
  редактируется.
* Ответ черновика больше не содержит строку листа целиком. Раньше в нём были поля-даты и
  служебное поле `__row`, и `google.script.run` мог вернуть пустой ответ.

## Интерфейс

На складе появилась карточка «Приход по накладной». В ней:

* загрузка фото или PDF;
* реквизиты документа и выбор поставщика (найденный в документе подставлен);
* строки: продукт (сначала похожие, затем вся номенклатура), количество, цена, даты, источник
  сопоставления и процент, кнопка срока по справочнику, скан этикетки, «не принимать»;
* сумма принимаемых строк против итога документа;
* «Сохранить и проверить», «Провести приход»;
* список незавершённых приходов.

Старая карточка приёмки, которая выводила сырой JSON внизу каждого экрана, удалена.

## Новые действия API

* `UPDATE_INVOICE_DRAFT`, `SCAN_INVOICE_LINE_LABEL` — модуль `warehouse_receive`.
* `GET_INVOICE_DRAFTS` — модуль `warehouse_view`.
* Распознавание по-прежнему запускается через `SCAN_INVOICE_PREVIEW`, проводка — через
  `CONFIRM_INVOICE_RECEIPT`.

## Проверено

Прогон в Node на настоящих модулях InvoiceRecognitionCore, InvoiceOcr, EnterpriseIntake,
OperationalClosureStage11, OperationalHardeningStage12, Products, Suppliers и OcrYandex;
OCR и модель подменены.

* Снимок с наклоном 3 %: таблица восстановлена построчно.
* Поставщик найден. «Сл1вки…» → «Сливки 33 %…» (нечёткое совпадение, 92 %), масло — точное
  совпадение, креветки — не найдены. Продукт другой организации не виден.
* Подсказка срока из справочника. Второй проход-аудит добавил своё предупреждение.
* `PARTIAL`: без согласия проводка отклоняется. «Не принимать» строку 3 → `READY`.
* Ручной выбор продукта → соответствие запомнено → следующий черновик сопоставлен по нему.
  Другая организация этого соответствия не видит.
* Проводка: 2 партии. Повторная загрузка того же документа → `BLOCKED` (CONFLICT).
* Модель недоступна → строки разобраны шаблоном.
* Отклоняются: неверная дата, продукт чужой организации.
* В Chromium (ширина 430 px) пройден весь путь: распознавание, срок по справочнику, частичная
  проводка, дубль, ручной выбор с запоминанием, скан этикетки (даты и штрихкод), проводка,
  список черновиков. Ошибок на странице нет.

Регрессионные прогоны ТУ, норм, импорта ТТК, техкарт ПФ и журналов ККТ проходят. ESLint чистый.

## После деплоя

1. Запустите `runAllMigrations()`: он создаст лист `OCR_ALIASES`.
2. В свойствах скрипта нужны `YANDEX_OCR_API_KEY` (или `YANDEX_API_KEY` / `YANDEX_OCR_IAM_TOKEN`)
   и `YANDEX_FOLDER_ID`.
3. Необязательные свойства: `INVOICE_LLM_MODEL` (другая модель YandexGPT) и
   `INVOICE_LLM_DISABLED = true` (только разбор шаблоном).
